# Blueprint Support 07 — Authentication, Authorization, Tenancy & Security (Parts J & K)

Documentation-based, non-intrusive review. Classifications: **CONFIRMED ISSUE / POTENTIAL RISK / UNVERIFIED CONTROL**.

## PART J — Authentication, authorization & tenant isolation

### J.1 Registration, login, sessions

- **Flows** [V]: seller `/api/auth/register` (tx: Seller onboarding + draft Store + Wallet + 4 CMS pages, auto-login); shopper `/api/auth/shopper/register|login` (cross-portal email-collision check vs Seller/Admin; suspended 403; claims legacy guest orders by email — F-11); admin/seller shared `/api/auth/login` with `portal` switch; terminated **and suspended** seller 403 (the suspended-seller block landed with Task 22-b so suspend-revocation cannot be bypassed by re-login). **No email/phone verification; no MFA; no email-based password reset flow [M]**; self-service password CHANGE exists since Task 22-b (`POST /api/me/password` — verifies current password, rotates the session, returns the new token in the login JSON shape); no OAuth social login (the only OAuth is *seller→marketplace* connections).
- **Passwords** [V]: scrypt (`scryptSync`, 64-byte key, random 16-byte salt, `s1:salt:hash`), `timingSafeEqual` compare (`lib/password.ts:4-20`).
- **Sessions** [V]: DB `Session` row, token = 32-byte CSPRNG hex (`randomToken(32)`), fixed 7-day TTL, DB-revocable; cookie `sm_session`: `httpOnly, SameSite=None, Secure, path=/, maxAge=604800` (`lib/auth.ts`). **Stored sha256-hashed at rest (F-09, P1)**: `Session.token` = hex(sha256(raw)); every lookup goes through the hash-first `getSessionByToken()` helper — live-verified (lookup by raw finds nothing; digest-as-Bearer rejected). **Rotated + revocable since Task 22-b (R2, 2025-10-18)**: `rotateSession()` retires the presented token (cookie or Bearer, delete-first so the old token dies immediately) and issues a fresh one for the same principal — wired at `POST /api/me/password` (live proof: old token → 401 on guarded routes / `userType:null` on the session probe, new token → 200, DB row count for the old digest = 0); `revokeUserSessions(userType, userId)` deletes every live session for a principal and is wired on admin seller **suspend / terminate / reject** (audit `after.sessionsRevoked`) — live proofs: approved-then-suspended seller's Bearer token 401s immediately, terminated/rejected likewise, suspended re-login → `403 ACCOUNT_SUSPENDED`, terminated → `403 ACCOUNT_TERMINATED`. Admin role/isActive changes and a shopper-ban endpoint do not exist in this build — `requireAdmin` re-checks `isActive` and `requireShopper` re-checks `status==="active"` on every request, so deactivation is enforced without revocation. `destroySession()` (logout) honours the Bearer bridge as well as the cookie since Task 22-b. No per-device session list / no "logout everywhere" UI exists (helper ready if one is built). Residual **accepted**: the raw token still travels once in login JSON and is persisted in localStorage (`sm_session_token`) + Bearer for the sandbox iframe workaround — see F-09.
- **Dual-channel** [V]: `getSession()` accepts Bearer (regex `^[a-f0-9]{16,128}$`) **or** cookie; **no auth path trusts a client-supplied user id** — identity is always token→DB row; `X-Cart-Token`/`X-Shopper-Token` are device tokens used only for data reconciliation, never authorization (`checkout/owner.ts:20-40`, `cart/cart.ts:61-66`).
- **Suspension/recovery**: shopper suspended 403; seller lifecycle statuses gate login and portal UI; admin `isActive`. [V]

**Enforcement coverage** [V]:
- **Admin: 70/70 route files call a guard** (163 references; every file ≥2). RBAC caps separate superadmin/ops/finance/moderator (e.g. `payouts.manage` = superadmin+finance).
- **Store scoping: no IDOR found** — all 50 store routes session-guarded; every `[id]` route filters `storeId` or post-checks ownership (`ownProduct`, `ownVariant`, `ownCoupon`, `ownCollection`, `ownEndpoint`); inventory/variants verify `product.storeId === store.id`; wallet activity verified via `lines.some(l => l.walletId === wallet.id)`.
- **Shopper scoping**: `/api/me/orders*` scoped `shopperId: me.id` (404 otherwise); receive/return-request identical.
- **Portal escalation: blocked** — userType checked before any DB access; shopper token on seller/admin endpoints 401s; chat threads enforce shopper-XOR-store-owner.
- **Public routes**: `sf/**` (live stores, publishedJson only), `market/**`, `orders/lookup` (email+orderNumber pair; uniform 404; **sequential numbers ⇒ guessable**, F-08), `orders/receipt` (same pair; **PDF exposes full PII**), `checkout/payments/[ref]` status (random 16-hex ref), `img`, `health` (**exposes ledger problems**), `shipping/tick` (intentional, unauthenticated), `campaigns/active`, `webhooks/payments` (HMAC — see K.4), `import/**` (unauthenticated job creation — F-10), `sf/.../reviews` (**unauthenticated auto-published reviews**, E.2).

### J.3 Frontend vs server enforcement
All protection is **server-side** (route guards); frontend "protection" is UX only (portal shells, disabled buttons). Single-route SPA has no route-level auth middleware (no `middleware.ts` [M]). Deep links `?sf/?sp` are public by design. [V]

### K.4 Rate limiting & abuse [V → COVERED]

Image copy 10s/5MB. Limiter store is pluggable since Task 22-b (in-memory default; Redis adapter via `RATE_LIMIT_REDIS_URL` with warn-once in-memory fallback).

### K.6 Data protection & audit [V]

### K.7 Positive controls verified [V]
scrypt+timingSafeEqual passwords; 256-bit CSPRNG session tokens; sha256-hashed session tokens at rest (F-09); DB-revocable expiring sessions; session rotation on credential change + principal-wide revocation hooks on seller state transitions (Task 22-b, F-09); 100% admin guard coverage; consistent store/owner scoping (zero IDOR found); portal escalation blocked; AES-256-GCM sealed marketplace tokens (single-use refresh rotation); hashed single-use claim tokens in guarded transactions; fully parameterised DB access; no HTML injection sinks; SSRF private-range guard on the resolve path + per-redirect-hop re-validation on the image copier (F-06); webhook log-first; idempotent webhook status handling; required single-use seller-bound OAuth state (F-07); pluggable rate-limit store with outage-safe Redis fallback (Task 22-b, F-04).
