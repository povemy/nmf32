    11→## 0. Programme invariants (bind every phase)
    12→
    13→1. **Single generation only.** One nullable sponsor FK per `AffiliateProfile`, immutable after activation. No MLM depth, no recruitment bonuses, no click rewards. Nothing in any phase may add a second-level share.
    14→2. **Seller-funded pool.** Commission is carved from seller proceeds at checkout; platform commission is untouched. Invariant after Phase 4: `Σ sellerNet + Σ commission + Σ affiliatePool === orderTotal` per order.
    15→3. **Server-recorded attribution only.** Affiliate identity in money paths comes from server-side touch records keyed by the httpOnly `nm_ins_vid` visitor cookie (`src/lib/analytics/identity.ts`). No client-supplied affiliate ids.
    16→4. **Frozen snapshots.** Rate, pool, attribution are frozen per `OrderItem` at checkout create and never recomputed — same discipline as the existing commission snapshots (`src/lib/commission.ts`, `computeOrderCommissions`).
    17→5. **Immutable ledger.** All money movement goes through `src/lib/ledger.ts` recipes with `dedupKey` idempotency; affiliate state is derived, never authoritative over the ledger.
    18→6. **Manual payouts only.** No automated PSP payout exists or is assumed (`architecture-audit.md` §3.10).
    19→7. **Kill switch.** `affiliate.enabled` (Setting) gates every affiliate route and the checkout integration; false = programme inert, existing records preserved.

   157→### 1.7 AffiliateCommission + AffiliateCommissionEntry
   158→```prisma
   159→model AffiliateCommission {
   160→  id                String    @id @default(cuid())
   161→  orderItemId       String    @unique          // ONE commission row per OrderItem — idempotency anchor
   162→  orderId           String
   163→  affiliateId       String                     // the DIRECT affiliate (attribution winner)
   164→  storeId           String
   165→  // Frozen snapshot (copied from OrderItem affiliate columns — defence in depth)
   166→  rateBps           Int
   167→  baseMinor         Int                        // commissionable base B
   168→  poolMinor         Int                        // P = B × R, integer minor units
   169→  currency          String    @default("MYR")
   170→  // Lifecycle: pending → approved → available → paid; side states held | reversed
   171→  status            String    @default("pending")
   172→  approvedAt        DateTime?                  // set when order authoritative state = delivered|completed
   173→  availableAt       DateTime?                  // approvedAt + affiliate.review_days (clock for available)
   174→  paidAt            DateTime?
   175→  payoutId          String?                    // FK AffiliatePayout when paid
   176→  reversedMinor     Int       @default(0)      // cumulative reversal against this commission
   177→  recoveryMinor     Int       @default(0)      // late-refund recovery re-credited (offsets future earnings)
   178→  createdAt         DateTime  @default(now())
   179→  updatedAt         DateTime  @updatedAt
   180→
   181→  @@index([affiliateId, status])
   182→  @@index([orderId])
   183→}
   184→
   185→model AffiliateCommissionEntry {
   186→  id            String   @id @default(cuid())
   187→  commissionId  String
   188→  beneficiaryId String                       // AffiliateProfile.id receiving the share
   189→  role          String                       // "direct" | "sponsor" — EXACTLY the two allowed values
   190→  shareMinor    Int
   191→  status        String   @default("pending") // pending | approved | available | paid | held | reversed
   192→  heldReason    String?
   193→  paidAt        DateTime?
   194→  createdAt     DateTime @default(now())
   195→  updatedAt     DateTime @updatedAt
   196→
   197→  @@unique([commissionId, role])              // max 2 rows per commission, one per role
   198→  @@index([beneficiaryId, status])
   199→}
   200→```
   201→- `@@unique([commissionId, role])` structurally enforces "2 beneficiary rows max".
   202→- Split is computed **at posting** (webhook T1 time), not at checkout: sponsor eligibility is evaluated against sponsor status at posting (`commission-definitions.md` §4). No sponsor / sponsor ineligible / `affiliate.sponsor_enabled=false` → single `direct` row with `shareMinor = poolMinor`.
   203→- Entry status can diverge from commission status ONLY for `held` (sponsor under review — sponsor share held, direct 90% unaffected) and manual admin states.

   305→## 4. Phase 3 — Attribution + checkout integration
   306→
   307→**Goal:** product-sale attribution resolved server-side per item at checkout; snapshots frozen; self-purchase excluded.
   308→
   309→**Models:** `AffiliateAttributionTouch` (if not landed in Phase 2 with the track endpoint — it does), `OrderItem` affiliate snapshot columns.
   310→
   311→**Code changes (the only existing-file edits in the programme):**
   312→1. `src/app/api/checkout/create/route.ts` — inside `runCheckout`, after `computeGroupPricing` and before the transaction: resolve affiliate attribution **per line**:
   313→   - eligible = `affiliate.enabled` AND store `affiliateOptIn` AND (product `affiliateEnabled` OR store default applies) AND an attribution touch exists within `affiliate.attr_window_days`;
   314→   - resolve the LAST valid touch per (visitorId, productId) — one query per distinct product, `orderBy clickedAt desc, take 1`;
   315→   - self-purchase exclusion: touch.affiliateId === buyer's `AffiliateProfile.id` → exclude with reason `self_purchase`;
   316→   - rate: `Product.affiliateRateBps ?? Store.defaultRateBps`, clamped to `affiliate.max_rate_bps`; 0 or none → `not_enabled`/`store_opt_out` exclusion;
   317→   - compute `B` (commissionable base — the item's voucher/coupon-adjusted merchandise value, EXCLUDING shipping/tax/platform fees; see `commission-definitions.md` §2) and `P = B × R / 10000` (integer, floor at the pool step per definitions §3);
   318→   - pass the affiliate parts into the commission computation so `OrderItem.sellerNetMinor` is written **net of P** and the affiliate snapshot columns are written in the same `orderItem.createMany`.
   319→2. `src/lib/commission.ts` — `computeOrderCommissions` input gains an optional per-item `affiliate` block; the reconciliation target becomes `Σ sellerNet + Σ commission + Σ affiliatePool === orderTotal` (`reconcileSplits` extended — drift assignment to largest line unchanged).
   320→3. **Per-OrderItem independence in multi-seller checkout:** the PaymentGroup groups lines per SELLER, but attribution is per PRODUCT. Two items from the same seller may attribute to different affiliates (or one attributed, one not); items from different sellers never share attribution by construction. Attribution resolution therefore runs per `pricing.items` line, NOT per seller group, and the snapshot is written per `OrderItem`. This is the deliberate divergence from the seller-grouped money math — it is safe because every downstream consumer (commission row creation, T1 4th line, T5 reversal) reads the per-item snapshot, never a group aggregate.
   321→
   322→**Routes:** none new (checkout is the integration point). `GET /api/affiliate/attributions` (hub view of recent touches) is optional here or Phase 7.
   323→
   324→**UI:** none (checkout UX unchanged — attribution is invisible to the buyer).
   325→
   326→**Dependencies:** Phase 1+2; the visitor cookie must be readable server-side at checkout (`cookies()` — same mechanism as `resolveAttribution()` in `src/lib/analytics/attribution.ts`).
   327→
   328→**Exit criteria (staging):** multi-seller cart with mixed attribution/self-purchase/non-eligible items → `OrderItem` rows carry correct frozen snapshots; `Σ sellerNet + Σ commission + Σ pool === total` holds for every order (script assertion, pattern: `scripts/test-commission-parity.ts`).

   365→
   366→**Goal:** refund reversals proportional against original snapshots; manual affiliate payout workflow with references.
   367→
   368→**Models:** `AffiliatePayout`.

   370→**Code changes:**
   371→1. `src/app/api/admin/refunds/[id]/process/route.ts` — alongside T5: affiliate reversal derived from the order's `AffiliateCommission` rows using the SAME proportional allocation of the order-level refund amount across items (family: `allocateProportionally`, `src/lib/money.ts`), clamped so cumulative reversals never exceed each commission's remaining balance:
   372→   - `reversalItem = min(remainingItem, proportionalShare)`; residual re-clamped across items with remaining balance;
   373→   - entry-level reversal mirrors the commission-level split proportionally (`direct`/`sponsor` each reversed `round_half_up(reversal × share / pool)`, sponsor residual clamped, final residual to direct so `Σ reversals === commission reversal`);

   375→   - **late-refund recovery**: reversal against an already-`paid` commission creates a negative `recoveryMinor` obligation on the affiliate profile that offsets FUTURE earnings at posting time (never claws back money already transferred — finance-ops decision documented in `commission-definitions.md` §7).

   378→   - `POST /api/affiliate/payouts` — request; rate limit **3/min per account**; validates amount ≥ `affiliate.min_payout_minor`, ≤ available balance (ledger-derived), one open request (Serializable + bounded P2034 retry); NO ledger movement yet;
