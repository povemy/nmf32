     9→     9→## 0. Programme invariants (bind every phase)
    10→    10→
    11→    11→1. **Single generation only.** One nullable sponsor FK per `AffiliateProfile`, immutable after activation. No MLM depth, no recruitment bonuses, no click rewards. Nothing in any phase may add a second-level share.
    12→    12→2. **Seller-funded pool.** Commission is carved from seller proceeds at checkout; platform commission is untouched. Invariant after Phase 4: `Σ sellerNet + Σ commission + Σ affiliatePool === orderTotal` per order.
    13→    13→3. **Server-recorded attribution only.** Affiliate identity in money paths comes from server-side touch records keyed by the httpOnly `nm_ins_vid` visitor cookie (`src/lib/analytics/identity.ts`). No client-supplied affiliate ids.
    14→    14→4. **Frozen snapshots.** Rate, pool, attribution are frozen per `OrderItem` at checkout create and never recomputed — same discipline as the existing commission snapshots (`src/lib/commission.ts`, `computeOrderCommissions`).
    15→    15→5. **Immutable ledger.** All money movement goes through `src/lib/ledger.ts` recipes with `dedupKey` idempotency; affiliate state is derived, never authoritative over the ledger.
    16→    16→6. **Manual payouts only.** No automated PSP payout exists or is assumed (`architecture-audit.md` §3.10).
    17→    17→7. **Kill switch.** `affiliate.enabled` (Setting) gates every affiliate route and the checkout integration; false = programme inert, existing records preserved.

   155→   155→### 1.7 AffiliateCommission + AffiliateCommissionEntry
   156→   156→```prisma
   157→   157→model AffiliateCommission {
   158→   158→  id                String    @id @default(cuid())
   159→   159→  orderItemId       String    @unique          // ONE commission row per OrderItem — idempotency anchor
   160→   160→  orderId           String
   161→   161→  affiliateId       String                     // the DIRECT affiliate (attribution winner)

   163→   163→  // Frozen snapshot (copied from OrderItem affiliate columns — defence in depth)
   164→   164→  rateBps           Int
   165→   165→  baseMinor         Int                        // commissionable base B
   166→   166→  poolMinor         Int                        // P = B × R, integer minor units
   167→   167→  currency          String    @default("MYR")
   168→   168→  // Lifecycle: pending → approved → available → paid; side states held | reversed
   169→   169→  status            String    @default("pending")
   170→   170→  approvedAt        DateTime?                  // set when order authoritative state = delivered|completed
   171→   171→  availableAt       DateTime?                  // approvedAt + affiliate.review_days (clock for available)
   172→   172→  paidAt            DateTime?
   173→   173→  payoutId          String?                    // FK AffiliatePayout when paid
   174→   174→  reversedMinor     Int       @default(0)      // cumulative reversal against this commission
   175→   175→  recoveryMinor     Int       @default(0)      // late-refund recovery re-credited (offsets future earnings)
   176→   176→  createdAt         DateTime  @default(now())
   177→   177→  updatedAt         DateTime  @updatedAt
   178→   178→
   179→   179→  @@index([affiliateId, status])
   180→   180→  @@index([orderId])
   181→   181→}
   182→   182→
   183→   183→model AffiliateCommissionEntry {
   184→   184→  id            String   @id @default(cuid())
   185→   185→  commissionId  String
   186→   186→  beneficiaryId String                       // AffiliateProfile.id receiving the share
   187→   187→  role          String                       // "direct" | "sponsor" — EXACTLY the two allowed values
   188→   188→  shareMinor    Int
   189→   189→  status        String   @default("pending") // pending | approved | available | paid | held | reversed
   190→   190→  heldReason    String?
   191→   191→  paidAt        DateTime?
   192→   192→  createdAt     DateTime @default(now())
   193→   193→  updatedAt     DateTime @updatedAt
   194→   194→
   195→   195→  @@unique([commissionId, role])              // max 2 rows per commission, one per role
   196→   196→  @@index([beneficiaryId, status])
   197→   197→}
   198→   198→```
   199→   199→- `@@unique([commissionId, role])` structurally enforces "2 beneficiary rows max".
   200→   200→- Split is computed **at posting** (webhook T1 time), not at checkout: sponsor eligibility is evaluated against sponsor status at posting (`commission-definitions.md` §4). No sponsor / sponsor ineligible / `affiliate.sponsor_enabled=false` → single `direct` row with `shareMinor = poolMinor`.
   201→   201→- Entry status can diverge from commission status ONLY for `held` (sponsor under review — sponsor share held, direct 90% unaffected) and manual admin states.

   303→   303→## 4. Phase 3 — Attribution + checkout integration
   304→   304→
   305→   305→**Goal:** product-sale attribution resolved server-side per item at checkout; snapshots frozen; self-purchase excluded.
   306→   306→
   307→   307→**Models:** `AffiliateAttributionTouch` (if not landed in Phase 2 with the track endpoint — it does), `OrderItem` affiliate snapshot columns.
   308→   308→
   309→   309→**Code changes (the only existing-file edits in the programme):**
   310→   310→1. `src/app/api/checkout/create/route.ts` — inside `runCheckout`, after `computeGroupPricing` and before the transaction: resolve affiliate attribution **per line**:
   311→   311→   - eligible = `affiliate.enabled` AND store `affiliateOptIn` AND (product `affiliateEnabled` OR store default applies) AND an attribution touch exists within `affiliate.attr_window_days`;
   312→   312→   - resolve the LAST valid touch per (visitorId, productId) — one query per distinct product, `orderBy clickedAt desc, take 1`;
   313→   313→   - self-purchase exclusion: touch.affiliateId === buyer's `AffiliateProfile.id` → exclude with reason `self_purchase`;
   314→   314→   - rate: `Product.affiliateRateBps ?? Store.defaultRateBps`, clamped to `affiliate.max_rate_bps`; 0 or none → `not_enabled`/`store_opt_out` exclusion;
   315→   315→   - compute `B` (commissionable base — the item's voucher/coupon-adjusted merchandise value, EXCLUDING shipping/tax/platform fees; see `commission-definitions.md` §2) and `P = B × R / 10000` (integer, floor at the pool step per definitions §3);
   316→   316→   - pass the affiliate parts into the commission computation so `OrderItem.sellerNetMinor` is written **net of P** and the affiliate snapshot columns are written in the same `orderItem.createMany`.
   317→   317→2. `src/lib/commission.ts` — `computeOrderCommissions` input gains an optional per-item `affiliate` block; the reconciliation target becomes `Σ sellerNet + Σ commission + Σ affiliatePool === orderTotal` (`reconcileSplits` extended — drift assignment to largest line unchanged).
   318→   318→3. **Per-OrderItem independence in multi-seller checkout:** the PaymentGroup groups lines per SELLER, but attribution is per PRODUCT. Two items from the same seller may attribute to different affiliates (or one attributed, one not); items from different sellers never share attribution by construction. Attribution resolution therefore runs per `pricing.items` line, NOT per seller group, and the snapshot is written per `OrderItem`. This is the deliberate divergence from the seller-grouped money math — it is safe because every downstream consumer (commission row creation, T1 4th line, T5 reversal) reads the per-item snapshot, never a group aggregate.
