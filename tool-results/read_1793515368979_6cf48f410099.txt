     7→## A. Executive summary
     8→
     9→Phase 2 made NOMOFEE materially faster and more operationally reliable **without weakening any Phase 1 mechanism** (verified: ledger recipes/dedupKeys untouched, CAS oversell guard intact per-line inside the checkout transaction, CSRF gate untouched, rate limits preserved and strengthened):
    10→
    11→- **Checkout query diet (A2):** the commission N+1 — the dominant pre-transaction cost, ≈5+2·D sequential queries **per line** (D = category depth; a 5-line cart ≈ 40 sequential queries, measured **1535 ms**) — was replaced by a batched context loader (~6 fixed round-trips for the whole cart, **140 ms measured**, an **11× improvement**), with **byte-identical resolution proven by a 20-check parity gate** against a verbatim copy of the sequential resolver. Idempotency replays, pricing reads, voucher wallet reads, in-tx re-validation, inventory logging and post-commit fan-out were all consolidated; the post-commit orders re-read was eliminated entirely. The per-line conditional stock decrement (oversell guard) is **deliberately unchanged**.
    12→- **Maintenance off the buyer's path (A5):** the two lazy sweeps that used to run inside `GET /api/me/orders` (a GLOBAL auto-complete sweep + a tracking tick — up to ~250 sequential queries on a shopper's latency budget whenever the 60 s throttle expired) moved to the scheduler rail (`/api/cron/order-maintenance`, 30 s cadence, durable-tick pattern). The route now answers in **~630–750 ms with zero maintenance work** (remote-Supabase dev environment).
    13→- **Dead safety net revived:** the affiliate lifecycle tick (`sweepAffiliateLifecycle` — approves/matures affiliate commissions) was defined in the scheduler's ROUTES but **never ticked** (state.json: `ticks: 0`). It is now wired and live-verified (first successful tick recorded).
    14→- **Public read caching (C):** a tag-based data-cache layer (`src/lib/public-cache.ts`, Next 16 official `unstable_cache` + `revalidateTag(tag, {expire: 0})`) now serves the 8 highest-traffic public routes with 30–60 s TTLs. Measured hit improvements: market/products **471→19 ms (25×)**, search/suggest **672→25 ms (27×)**, storefront home **1226→62 ms (20×)**. Invalidation from seller mutation routes is **immediate** (live-verified: product PATCH → next PDP request serves fresh data) with the TTL as the self-healing safety net (live-verified).
    15→- **Indexes (B):** 7 evidence-backed indexes authored in migration `20261102000000_phase2_performance_indexes` (CREATED, NOT APPLIED) — including the two carried over from the Phase 1 handoff (`PaymentGroup [status,expiresAt]`, `Order [storeId,status]`) and one index replacement (`PaymentWebhookLog [processed] → [processed,createdAt]`).
    16→- **Resource safety (D):** both rate limiter stores gained hard capacity bounds with amortized-O(1) eviction (randomized-identity attack backstop, unit-tested); the chat hub's per-socket 500 ms refill timer became a lazy timestamp token-bucket (identical limiting semantics, zero timers — 2000 wake-ups/s eliminated at 1000 sockets). Documented no-change decisions: WS connection consolidation, countdown isolation, PDF architecture.
    17→- **Dependency & file hygiene (E):** 15 verified-unused packages removed (lockfile consistent) and 18 orphaned files deleted — separately sequenced per protocol, each verified by tsc + dev-server boot + route smoke tests. **OSV audit: 0 advisories across the checked top-level production set** (next 16.4.3, sharp 0.35.5, zod 4.6.7, undici 8.12.3, prisma 6.19.2, react 19.2, socket.io 4.8.4, …).
    18→- **Financial verification (F):** the FIN-4 gate — 33 checks across webhook idempotency, payout exactly-once, refund caps, reconciliation, invariants — was **fixed to be deterministic** (the insufficient-wallet probe's zero-balance precondition had drifted; now enforced via an audited reserve-then-release payout drain) and **passes completely**. PSP reality documented: all rails are sandbox-mock; a 12-case provider-sandbox test plan was authored (`docs/psp/psp-sandbox-test-plan.md`), NOT executed.
    19→
    20→Net effect: the buyer-facing hot paths (market, search, storefront, PDP) are an order of magnitude cheaper under load; checkout's database cost is bounded and item-count-independent in its dominant phase; marketplace upkeep no longer taxes shoppers; the affiliate commission lifecycle is actually maintained; and the money pipeline is re-proven end-to-end through the optimized code.

    36→### B.2 Changes (every financial/inventory guard preserved)
    37→
    38→| Optimization | Before | After | Correctness argument |
    39→|---|---|---|---|
    40→| **Commission rate context** (`lib/commission.ts`: `loadRateContext` + `resolveRateFromContext`) | (5+2·D) sequential queries **per line per group**; no cache despite a comment claiming one; the previously-built batched loader had been lost (its parity script was broken) | **~6 fixed round-trips for the entire checkout** (settings+sellers+products+holidays+seed categories in one parallel batch → parent-closure chase rounds → scoped overrides), pure in-memory resolution per item | **Byte-identical** to the sequential resolver — proven by `scripts/test-commission-parity.ts`: 15 synthetic branches (incl. F-08 scoped-override precedence, holdDays/fixedFee-only rows, cycle-safe chains), 74 DB-backed catalog cases, 20 product-derived-seed robustness cases, full 5-line path parity + Option B invariant |
    41→| **Idempotency replays** | 2 sequential unique lookups | 1 parallel batch | Both are unique-key reads; group checked first, order second — same semantics |
    42→| **Pricing** (`checkout/pricing.ts`) | variants → `store.findMany` → coupon row **re-fetched per group** | store data from the variant→product→store include (the separate `store.findMany` was fully redundant); coupon row fetched **once** in the same parallel batch as variants; per-group verdicts are pure (`couponVerdict`, one clock) | Same rows, same verdict math, same "highest-subtotal eligible group wins" rule; group/store live-status checks preserved |
    43→| **Voucher wallet reads** (`lib/vouchers.ts`) | one `userVoucher.findFirst` per entry, sequential | **one `findMany`** for all entries (ids unique; userId filter identical) | Same rows, same status gates, same verdict math, same hard-mode error order |
    44→| **Affiliate settings** | `getAffiliateSettings()` fetched twice per checkout (route + inside resolver) | fetched once, passed in | Same settings object semantics |
    45→| **Cart token read** | full deep include of every cart line (variant→product→store graph) for one string | `select: { token: true }` | Same value; `Cart.shopperId` is unique |
    46→| **In-tx fast-fail re-validation** | per-line `findUnique` | one `findMany` (id IN) + per-line check | Same 409 conditions in the same order; the authoritative guard remains the CAS decrement |
    47→| **Inventory logs** | one `create` per line | one `createMany` per seller group | Identical rows (reason/refId shape preserved) |
    48→| **salesCount increments** | one `update` per line | aggregated per distinct product | increment(a)+increment(b) ≡ increment(a+b) |
    49→| **Post-commit fan-out** | orders re-read (`findMany` + store include) then sequential notify/logActivity per order | summary returned **from inside the tx** (no re-read window); notify+logActivity in parallel per order | Same notification content/audit meta; F1 post-commit placement preserved |
    50→| **Checkout timing instrumentation** (`lib/checkout-timing.ts`) | authored in a previous cycle, imported by nothing (dead) | **wired into the route** — one JSON anatomy line per checkout when `CHECKOUT_TIMING=1` (phase marks, tx acquire/exec/statement count, gate stats, loop lag), emitted on success and error paths | Observation only; zero behavior change; validated live (see B.6) |
    51→
    52→**Untouched by design:** the per-line conditional `updateMany … WHERE stock >= qty` oversell guard (one statement per line, exactly as before — the correctness core); voucher redemption status/quota guards; coupon redemption; the 15 s tx timeout; the admission gate placement (replays bypass it, everything else inside); response shapes (verified by E2E + FIN-4).

    54→### B.3 Transaction isolation — discrepancy resolved
    55→
    56→| Path | Isolation (verified in code) | Why it is appropriate |
    57→|---|---|---|
    58→| **Checkout creation** | **READ COMMITTED** (Prisma default — no `isolationLevel` on the `db.$transaction`) | Every invariant that matters here is enforced by atomic row-locked conditional writes (stock decrement `WHERE stock >= qty`, voucher `WHERE status='AVAILABLE'`, quota `WHERE claimedCount < quota`), which are exactly correct under READ COMMITTED. The "Serializable checkout" from the earlier assessment was **wrong for checkout-create** — Serializable there would only add serialization failures precisely in the launch-rush scenario this design optimizes for. No change. |
    59→| **Payment confirmation** (group + legacy intents) | **SERIALIZABLE** + claim-first conditional `updateMany` + inline P2034 retry (3 attempts, jittered) + `SET LOCAL statement_timeout='10s'` | Multi-row financial invariants (wallet credits, ledger postings, affiliate commissions, cart clearing) with phantom risk; exhaustion returns 503 so the PSP retries. |
    60→| **Payout events / batches / seller payouts** | **SERIALIZABLE** via `withSerializableTxRetry` (bounded retries) | Reservation + wallet mutation exactly-once. |
    61→| **Refund processing** | READ COMMITTED + **explicit `SELECT … FOR UPDATE`** on the order row + re-read under lock | The cumulative cap and wallet sufficiency are order/wallet-level invariants a per-row claim cannot protect; the pessimistic lock serializes concurrent refunds per order with a documented deadlock-free lock order. |
    62→| **Order maintenance cron (new)** | READ COMMITTED (`transitionOrder`) | Candidate filter excludes completed orders; duplicate runs are no-ops. |
    63→
    64→**No isolation level was changed anywhere in Phase 2.** The discrepancy is resolved as a documentation error in the prior assessment, not a code defect.

    66→### B.4 Connection management — assessment (no change)
    67→
    68→Facts re-verified: a **single** Next.js process holds the only Prisma pool (`connection_limit=10` in `SUPABASE_DATABASE_URL`, Supavisor **session** mode, PG `max_connections=60`, per-user session ceiling measured at 15); the chat hub and the scheduler hold **zero** DB connections (HTTP/relay only). The admission gate (`MAX_INFLIGHT=8`, queue 32, wait 5 s) keeps checkout below the pool size with headroom for cron/public reads — the deliberate throttle for the 1×1 topology. **Decision: no change.** Raising `connection_limit` would press the Supavisor per-user ceiling; raising `MAX_INFLIGHT` without a pool change would starve non-checkout traffic. The A2 round-trip diet *reduces* per-checkout pool hold time (8 tx statements, shorter pre-tx phase), which is the correct direction. Transaction-pooler assumptions were **not** introduced anywhere.

    71→
    72→1. Per-statement remote RTT dominates (dev measured ~80–150 ms/statement; production with co-located DB will differ materially) — the tx itself is now 8 statements for a 1-line order and grows only with lines (+1 CAS per line) and groups (+~6 per extra seller group).
    73→2. The checkout admission gate and both rate limiter stores remain **single-process** — fine at 1×1, must move to shared state before horizontal scaling (documented, unchanged from prior topology notes).
    74→3. Post-commit notify/logActivity still costs ~2 writes per order (now parallel) — bounded, non-critical path.
    75→4. Storefront search is `contains`-based (no trigram/FTS index) — flagged for staging evaluation, not addressed (would need `pg_trgm`; out of Phase 2's no-new-infrastructure scope).

   105→### C.3 Invalidation (live-verified)
   106→

   109→### C.4 Deliberately excluded (C2 safety)
   110→
   111→All `me/*`, `cart/*`, `checkout/*`, `store/*`, `admin/*`, `affiliate/*` (private), `orders/lookup|receipt`, webhooks, cron. **Purity boundaries enforced:** the storefront/PDP view trackers (cookie writes) run OUTSIDE the cached loaders. Displayed prices/stock are advisory only — **checkout re-validates both transactionally** (CAS decrement + in-tx revalidation), so cache staleness can never oversell or mischarge.
