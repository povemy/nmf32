    15→## 0. Executive summary
    16→
    17→**Scale of the audit:** 200+ API routes, 3 portals (admin / seller / buyer), public storefront, 2 mini-services (chat hub + expiry scheduler), Caddy gateway, Prisma schema, and every platform-controlled attribute from `Setting`, `CommissionSetting`, seller overrides, and feature flags.
    18→
    19→**Headline results:**
    20→
    21→1. **The original issue class (settings sync) is largely FIXED for seller-facing platform terms** — the `seller-terms.ts` SSOT introduced previously is wired into every seller surface and returns live values at runtime. **1 stale literal remains** (seller wallet "RM 50" hint vs live RM 10 minimum).
    22→2. **However, the same defect class recurs in 7 other places** where admin-editable or admin-implied values are **not actually wired to enforcement** — the worst being the entire **Commission Overrides admin surface (FIN-02), the Feature Flags page, and `analytics.retention_days`**, where an admin edits values that running code never reads (§2.3).
    23→3. **Auth baseline is structurally sound** — every `/api/admin/**` and `/api/store/**` route has a session guard (verified: zero unguarded routes), tenant isolation on seller routes is complete (zero cross-tenant reads/writes found), and buyer ownership checks all pass (§3).
    24→4. **But four CRITICAL gaps undermine that baseline**: (a) the payment-webhook signing secret fails open to a publicly documented demo constant; (b) `SameSite=None` cookies with zero CSRF/origin validation anywhere; (c) seller suspension is cosmetic (no status enforcement, no session revocation, suspended sellers can re-login and even re-publish their store); (d) the password-change endpoint is broken at compile time (`rotateSession` does not exist → runtime 500).
    25→5. **Runtime probes:** 10/10 unauthorised guard probes returned 401 (PASS); live platform terms returned configured values (PASS); the anonymous-review integrity hole was **reproduced live** (FAIL — then cleaned up); order-lookup enumeration throttle absence confirmed.
    26→
    27→**Finding counts:** 4 CRITICAL · 7 HIGH · 13 MEDIUM · 15 LOW (grouped; full register in §5).

Suspend sets the store to `draft`, but `POST /api/store/publish` re-publishes `draft→live` with **no seller-status check** (`store/publish/route.ts:10-28`; `canPublish` checks products/support-email/SEO only, `store-lifecycle.ts:96-118`) → **a suspended seller can self-un-suspend their storefront**.
   195→6. The suspended/terminated block in the UI is **client-side only** (`seller-shell.tsx:175-190`).
   196→
   197→**Net effect: suspension is cosmetic. A suspended seller retains (and can re-obtain) full API access — fulfill/ship orders, request payouts, edit products, and re-publish the store.** Contrast: admin (`isActive`) and shopper (`active`) status ARE enforced at request time (`auth.ts:82,120`).
   198→
   199→Also **F-06 (HIGH)**: no admin route exists to ban a shopper at all (only login/profile/password touch `ShopperUser`), and expired Session rows are never purged.

   201→### 3.5 CSRF posture — **F-01 (CRITICAL)**
   202→
   203→- Session cookie: `httpOnly, sameSite:"none", secure:true` (`auth.ts:34-42`) — **attached to every cross-site request**.
   204→- **No `middleware.ts` / `proxy.ts` exists** (glob-verified); **zero** origin/referer validation, CSRF tokens, or `Sec-Fetch-Site` checks anywhere in `src/` (grep-verified).
   205→- Route bodies parse via `req.json()` with no content-type enforcement → cross-site `text/plain` form POSTs deliver the cookie and a parseable body (INFERRED from undici semantics — not live-tested).
   206→- Exposure set: **every cookie-authenticated POST/PATCH/DELETE** — including admin suspend/terminate/payout-approve/wallet-adjust, seller mutations, shopper checkout. Login CSRF (session fixation into an attacker account) also possible.
   207→- The Bearer-header path is CSRF-safe (custom header → preflight), but cookie is the default for top-level browsing.
