# P2.2-6/7/9 — Phase 2.2 verified audit fixes (C2.4 + two C3s)

Scope: three surgical, audit-verified fixes in the NOMOFEE codebase. No schema changes, no

## FIX 1 — C2.4: chat hub-auth rate limiting (shared `unknown` bucket outage)

**Files changed**
- `src/app/api/chat/hub-auth/route.ts`
- `src/lib/rate-limit.ts` (doc-only addition to the existing `rateLimitKey`)

**Root cause recap** — the chat hub mini-service calls hub-auth over loopback with NO client-IP
header, so every call landed in ONE shared bucket `chat-hub-auth:unknown` @ 120/min; a browser
reconnect storm (`reconnectionAttempts: Infinity`) exhausted it → 429 → hub disconnect →
infinite retry → platform-wide chat outage.

**Fix — exact key derivation + limits (two-tier, both reusing the existing bounded
`InMemoryRateLimitStore` / `rateLimitKey`, no new store):**
1. **Tier 1 (global per-IP backstop):** `rateLimit(req, "chat-hub-auth", 600)` — key
   `chat-hub-auth:{clientIp(req)}` (the shared `unknown` bucket in practice), raised 120→600/min.
   Bounds the session DB lookups a token-spray attacker (unlimited unique tokens) can force.
2. **Tier 2 (per-credential identity):** `rateLimitKey(sha256Hex(token).slice(0, 24),
   "chat-hub-auth:t", 120)` — key `chat-hub-auth:t:<first 24 hex of sha256(token)>` @ 120/min.
   Applied BEFORE the session lookup (repeated identical tokens, valid or not, are bounded before
   any DB work). The full `tokenHash` is computed once and doubles as the `Session.token`
   (sha256) lookup value — the previous inline `createHash("sha256")...digest("hex")` and the
   `crypto` import were replaced by `sha256Hex` from `@/lib/secretbox` (identical semantics).

**Constraint compliance:** identity is derived ONLY from the presented credential (never raw —
hashed first; `rateLimitKey` doc now states "keys must never be raw secrets — hash first");
no client-supplied identity headers are trusted; one shopper can no longer consume another's
quota (each credential has its own bucket); fail-closed 401 semantics, TOKEN_RE gate, response
shape, and all room-authorization logic unchanged; `mini-services/chat-service/index.ts`
deliberately NOT modified (identity comes from the credential, so IP forwarding is unnecessary —
and the hub must not be trusted to forward identity headers anyway).

**Live verification** (dev server, direct POSTs): 130 requests with one bogus 32-hex token →
exactly 120×401 then 10×429 (Tier 2 tripped); immediately after, 5 requests with 5 DISTINCT
bogus tokens → all 401 (own buckets — the old shared bucket would have 429'd them all).

## FIX 2 — C3: inventory adjustment read-modify-write → atomic CAS

**File changed:** `src/app/api/store/inventory/adjust/route.ts`

**CAS semantics:** replaced `newStock = variant.stock + delta` (JS) + unconditional
`update({... stock: newStock})` with ONE conditional UPDATE inside an interactive
`db.$transaction`:
- delta < 0 → `tx.productVariant.updateMany({ where: { id, stock: { gte: -delta } }, data:
  { stock: { increment: delta } } })`
- delta ≥ 0 → same call without the `gte` guard (plain atomic increment)
- `moved.count === 0` → `throw new ApiError(409, "INSUFFICIENT_STOCK", "Stock cannot go below 0
  (current ${variant.stock}, delta ${delta})")` (code+message preserved; status now 409 per the
  CAS contract, mirroring checkout/create's oversell guard). The thrown 409 rolls the tx back
  (no-op: 0 rows matched, log not yet written).
- `InventoryLog` created in the SAME tx — records only the delta that actually applied
  (+ reason field preserved).
- Read-back via `findUniqueOrThrow` INSIDE the tx (count>0 guarantees existence) so the response
  reports the stock THIS adjustment produced; response shape `{ id, stock, lowStock }` unchanged.
- Low-stock `notify` (inapp, `me.email`) still fires outside the tx, now keyed on the fresh
  post-CAS stock; ownership pre-check (404), `requireActiveSellerStore`, `variantId`/reason
  defaults, and `bustPublicCacheSafe(PUBLIC_CACHE_TAGS.products)` all preserved.

**Validation hardening:** `delta` must be a genuine `Number.isSafeInteger` NUMBER
(`typeof body.delta === "number"`) — the old `Math.round(Number(...))` coercion accepted
numeric strings and rounded fractional deltas; plus a new `|delta| ≤ 1,000,000` magnitude cap
(`stock` is a Prisma Int) → 400 VALIDATION "delta magnitude must not exceed 1,000,000".

**Live verification** (seeded seller lumina@nomofee.io, variant stock 20): `"5"`/`5.5`/`0` →
400 VALIDATION; `2000000` → 400 magnitude; 10 CONCURRENT −5 adjustments against stock 23 →
exactly 4×200 (23→3) + 6×409 INSUFFICIENT_STOCK, never negative, no lost updates (the old code
would have let all 10 compute from stale reads and overwrite each other); single −30 → 409;
stock restored to exactly 20 afterwards.

## FIX 3 — C3: secretbox production fail-closed

**Files changed:** `src/lib/secretbox.ts`, `.env.example`

**Fail-closed condition:** in `getKey()`, when `IMPORT_TOKEN_ENC_KEY` is unset/short AND
`process.env.NODE_ENV === "production"` → `throw new ApiError(503, "SECRETBOX_NOT_CONFIGURED",
"IMPORT_TOKEN_ENC_KEY is not configured — encrypted marketplace token storage is disabled
(fail closed)")` — mirrors the `mfa.ts` MFA_NOT_CONFIGURED pattern. Dev keeps the documented
deterministic fallback + one-time console.warn. `cachedKey` is never populated on the throw path
(fails closed on every call, not just the first).

**Import-cycle check (verified, no cycle):** `secretbox.ts` → `api.ts` → { next/server,
@prisma/client, ./db }; `db.ts` imports only `@prisma/client`; nothing in that graph imports
secretbox. The `ApiError` import is therefore safe (noted in a code comment).

**Additional surgical hardening (required for real fail-closure):** in `openSecret`, `getKey()`
is now resolved BEFORE the try/catch — previously the catch would have swallowed a
SECRETBOX_NOT_CONFIGURED throw into the tamper→null path, silently degrading decryption to
"no token stored" instead of 503. sealSecret has no try/catch (throw propagates). Helper
exports (`sha256Hex`, `randomToken`, `safeEqual`) do not touch `getKey()` and are unaffected —
safe to import from hub-auth even when the enc key is unconfigured.

**Docs:** header comment now documents the fail-closed behavior + key-rotation strategy
(single "v1:" key = sha256(IMPORT_TOKEN_ENC_KEY), no dual-key reading; rotation = set a NEW
key + run a decrypt+re-encrypt maintenance script during a short freeze — pre-rotation v1 rows
are unreadable after the swap, hence the freeze). `.env.example` (was "unset logs a warning and
derives a dev-only key") now documents the production fail-closed 503.

**Live verification:** `NODE_ENV=production` bun import of secretbox → `sealSecret` throws
ApiError 503 SECRETBOX_NOT_CONFIGURED with the exact message; dev mode → one-time warn +
seal/open roundtrip OK + tamper → null preserved.
