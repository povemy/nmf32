## Audit verdict per spec item

1. **Guest email verification before order creation — COMPLETE (no fix needed)**
   - `src/lib/guest-otp.ts`: purpose `"guest-checkout"` rides the shared
     issueEmailOtp/verifyEmailOtp machinery (CSPRNG uniform 6-digit code,
     keyed HMAC codeHash with day-bucket rollover, CAS attempt counter
     capped at 5 with carry-over, CAS DELETE consume → exactly-once).
     New `issueGuestCheckoutToken`/`verifyGuestCheckoutToken`: domain
     `"gcv:v1:"` (distinct from `"oag:v1:"` grants and `"otp:v1:"` hashes),
     HMAC-SHA256(EMAIL_OTP_SECRET, "gcv:v1:<email>:<expiryMs>"), email
     base64url-encoded in the body, 30-min TTL (`GUEST_CHECKOUT_TOKEN_TTL_MS`),
     constant-time `safeEqualHex` MAC compare, strict shape checks.
   - `src/app/api/checkout/guest-verify/request/route.ts`: delivery goes
     through `requireEmailChannel()` — the exact same `TransactionalEmailChannel`
     seam as `/api/orders/otp/request` (no fake delivery, no real emails;
     dev → uniform 503 EMAIL_PROVIDER_NOT_CONFIGURED, smoke-verified).
   - `src/app/api/checkout/guest-verify/verify/route.ts`: mints the token
     ONLY after a successful exactly-once consume; uniform 401 INVALID for
     every failure mode.
   - `src/app/api/checkout/create/route.ts`: guest branch requires
     `body.guestVerification` (401 GUEST_VERIFICATION_REQUIRED without it —
     smoke-verified, also with a FORGED well-shaped token) AND requires
     `customer.email === token.email` (400 otherwise). Fail-closed ordering
     verified: the gate fires BEFORE the PaymentGroup insert, so the
     pre-migration dev DB (missing nullable column) can never 500.

2. **Rate limiting — COMPLETE (no fix needed; live-verified)**
   - request: `rateLimit(req, "guest-verify-request", 5)` (5/min/IP) +
     `rateLimitKey(email, "guest-verify-email", 3, 3_600_000)` (3/h/email) —
     mirrors `/api/orders/otp/request` conventions (order-number axes dropped
     because there is no order yet — correct adaptation).
   - verify: 10/min/IP + 10/h/email — mirrors `/api/orders/otp/verify` (the
     per-order axis dropped likewise).
   - Live curl evidence: 6th request from one IP → 429; 4th request same
     email from DIFFERENT IPs → 429 (identity-keyed limiter works);
     verify route 11th → 429. No user-enumeration differences (uniform 401 /
     uniform 200-with-MESSAGE on the happy path; 400 only for syntactically
     malformed input, which carries no account knowledge).

3. **Guest carts — COMPLETE + FIXED-GAP (token echo)**
   - Token-keyed carts via "sm_cart" cookie / X-Cart-Token header
     (`src/app/api/cart/cart.ts`), lazy creation on first add
     (`ensureCartForCaller`), account carts unchanged for signed-in shoppers
     (`resolveCartCaller` preserves the exact requireShopper 401 semantics),
     no cart route 401s guests, GET /api/cart returns the token cart
     (smoke-verified end-to-end: add → 201 with items, GET → same cart,
     PATCH item, PATCH selection, DELETE all work with only the header).
   - **Fixed gap**: `shapeCart` now echoes `token` for GUEST carts only
     (`cart.shopperId == null ? cart.token : null`) so the client can adopt
     a server-side token rotation (defensive stale-token branch in
     `ensureCartForCaller` mints a fresh guest token when the header names an
     account-bound row; previously the client kept sending the stale header
     forever → cart read empty on every refresh + orphan rows on every add).
     Account carts echo `null` — a session-scoped row can never latch onto
     the guest identity.

4. **Login merge — COMPLETE + FIXED-GAP (client-side token retirement)**
   - `src/lib/shopper-merge.ts::mergeGuestCartForShopper`: re-point when the
     account has no cart, else upsert quantities (capped at 99/stock, no
     duplication) + delete the guest row; `clearCartToken()` retires the
     server cookie; best-effort (never fails login). Called from
     `/api/auth/shopper/login`, `/api/auth/shopper/register`,
     `/api/auth/unified-login`. `claimGuestStateForShopper` still gated on
     the durable shopper-email verification (getShopperEmailVerified —
     fail-closed pre-migration).
   - **Fixed gap**: the server retires its cookie at merge time, but the
     client's localStorage `sm_cart_token` (sent as X-Cart-Token on EVERY
     request via `deviceHeaders()`) was never retired — after login→logout
     the stale header named the re-pointed ACCOUNT-bound row → GET /api/cart
     empty forever + every add-to-cart minted an orphan guest row. Fix:
     new `clearDeviceCartToken()` in `src/lib/session-client.ts` (localStorage
     + in-memory memo), called from `unified-auth-panel.tsx::completeLogin`
     (shopper logins only) and `shopper-shell.tsx::submitRegister`.
   - Companion: new `syncCartToken()` mirrors an echoed guest-cart token into
     the device identity; wired into `applyServerCart` + `useCart().refresh`
     in `src/components/shopper/ui-bits.tsx` (also fixes the stale doc
     comment that claimed "guests have none" carts).
