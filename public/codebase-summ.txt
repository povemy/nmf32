1. PRODUCT OVERVIEW
--------------------------------------------------------------------------------
NOMOFEE is a Malaysia-focused multivendor marketplace (Shopee/Shopify hybrid):

  * SHOPPERS browse a central marketplace OR individual seller storefronts,
    buy from multiple sellers in ONE cart with ONE payment, chat with sellers,
    and manage orders in a buyer dashboard ("Me hub").
  * SELLERS get a Shopify-like backend: onboarding, product catalog with
    variants, inventory, order fulfilment, coupons, CMS page builder, themed
    storefronts with custom domains, SEO, webhooks/API keys, payouts wallet,
    marketplace-import tools, and buyer chat.
  * ADMINS run a command centre: seller KYC/approvals, product moderation,
    commission engine, refunds/disputes, payouts, ledger, coupons/banners,
    support tickets, reports, audit logs, feature flags.

Business model: marketplace facilitator. Platform commission (rate model
under config, see §9) deducted per order; sellers paid out from a
licensed-PSP split — the platform NEVER custodies buyer funds (see §9/§10).

2. TECHNOLOGY STACK & ARCHITECTURE
--------------------------------------------------------------------------------
  Framework    : Next.js 16 (App Router, Turbopack dev) + TypeScript 5 strict
  UI           : Tailwind CSS 4 + shadcn/ui (New York) + lucide-react icons
                 + framer-motion animations + zustand client state
  Data         : Prisma ORM 6 over SQLite (file db/custom.db)
                 * Money = Int minor units (cents). Percent = Float.
                 * Enums = String columns + app-level validation.
                 * JSON columns = String holding JSON (src/lib/json.ts).
                 * No Decimal in SQLite — this is why Int cents everywhere.
  Auth         : Custom DB-backed revocable sessions (NOT next-auth for the
                 portals; next-auth is installed but unused).
  Realtime     : socket.io mini-service (mini-services/chat-service, public
                 port 3003 behind a Caddy gateway; internal HTTP relay 3103)
                 used ONLY as a dumb broadcast hub; the Next.js API routes are
                 the authoritative chat persistence.
  PDF          : pdf-lib (order receipts).
  Single route : The whole product is ONE route (/) — a portal-switching SPA.
                 In production the three portals become separate hosts
                 (market/seller/admin.nomofee.io); the sandbox shows them as
                 surfaces of one page with a draggable portal FAB switcher.
  API style    : REST route handlers under src/app/api/**; uniform envelope
                 { ok, data | error:{code,message} } via src/lib/api.ts
                 (ok()/okPaged()/handle()/ApiError) + guard helpers.
  Runs with    : bun package manager; `bun run dev` (port 3000);
                 `bun run db:push` for schema; `bun run lint` for ESLint.

5. AUTHENTICATION & AUTHORIZATION — ALL ACCOUNT TYPES
--------------------------------------------------------------------------------
SESSION MECHANICS [LIVE]
  * DB-backed revocable sessions (Session table), TTL 7 days.
  * Delivery: httpOnly cookie "sm_session" (SameSite=None; Secure — survives
    cross-site iframe preview panels) OR "Authorization: Bearer <token>" from
    client localStorage bridge. Server accepts either (lib/auth.ts).
  * createSession(userType, userId) / destroySession / getSession.
  * Login rotates the session token; localStorage session key cleared on
    logout. Auth continuation callbacks read fresh auth from zustand at call
    time (stale-closure bug fixed in Task 6).

THREE ACCOUNT TYPES (userType on Session):
  1) admin   → requireAdmin(), requireAdminRole([roles]),
               requireCap(cap) with RBAC matrix ADMIN_CAPS:
                 sellers.approve/suspend  → superadmin, ops
                 products.moderate        → superadmin, ops, moderator
                 commission.manage        → superadmin, finance
                 payouts.manage           → superadmin, finance
                 refunds/disputes.manage  → superadmin, ops, finance
                 settings.manage          → superadmin only
                 impersonate              → superadmin only
  2) seller  → requireSeller(), requireActiveSellerStore() (approved/live store)
               Seller status lifecycle: pending→approved→suspended/terminated.
  3) shopper → requireShopper() (status must be active).

NO-GUEST-CHECKOUT POLICY [LIVE — root-cause fix for "session pollution" bugs]
  * Add-to-cart REQUIRES sign-in (guest add triggers a sign-in/register dialog,
    and the intended action auto-resumes after auth).
  * Carts, checkout, and the address book are strictly account-scoped
    (shopperId). Guests cannot create addresses or carts anymore.
  * claimGuestStateForShopper(): at login/registration, legacy GUEST orders
    (placed before this policy, matched by customerEmail) are claimed into the
    account. Address claiming was REMOVED — the old guest-address leaking into
    logged-in checkout is structurally impossible now.
  * One default address invariant enforced at login and on address ops.

SECURITY POSTURE
  * Guards on every portal API; admin capabilities checked per endpoint.
  * auditAdmin() writes AdminAuditLog for privileged actions.
  * Order/receipt lookup endpoints are token/ref-scoped.
  * KNOWN GAP: a full adversarial Auth/IDOR audit pass has NOT been done yet
    (spot checks were done during feature work). [DECIDED-NOT-BUILT — queued]

7.3 MULTI-SELLER SHOPPING & CHECKOUT [LIVE — verified E2E]
  1) Cart accepts items from MANY stores (single-store rule removed).
  2) Quote API returns per-store groups: subtotal, shipping (per-store
     free-shipping thresholds), coupon applicability (coupon wins on exactly
     ONE group — the highest eligible subtotal — so platform codes can't
     multiply across sellers).
  3) POST /api/checkout/create: ONE transaction creates a PaymentGroup
     (idempotency via idemKey) + N per-seller Orders (orderNumber per group,
     per-order idemKey `${key}:${storeId}`), OrderItems with COMMISSION
     SNAPSHOT per line (commissionPercent/Minor, fixedFee, sellerNetMinor),
     stock decrement + InventoryLog, salesCount bump, OrderStatusHistory,
     coupon redemptions, notifications, audit.
  4) Pay page: ONE charge for the group (mock PSP), retry/simulate endpoints
     group-aware.
  5) Webhook (mock PSP): payment.succeeded → group status+paidAt → per-order
     transition to paid → ledger T1 posting per order → store webhooks +
     notifications → cart cleared. payment.failed → group failed, orders stay
     payment_pending (retryable). All idempotent; every webhook logged
     (PaymentWebhookLog).

7.4 LEDGER & PAYOUTS [LIVE — accounting mirror, NOT custody]
  Double-entry engine (lib/ledger.ts). T1 on payment:
      debit  GATEWAY:{provider}          (full order total)
      credit SELLER:{walletId}:PAYABLE   (net after commission — pending hold)
      credit PLATFORM:REVENUE_COMMISSION (commission = PSP application fee)
  Balances with available_at > now are "pending" (the T+N settlement window).
  Payout pipeline: seller requests / admin batch → T2 clear (hold→available)
  → bank transfer record (mark-paid / fail). Admin ledger browser + wallets UI.

7.5 POST-PURCHASE [LIVE]
  Seller: fulfil → ship (carrier + tracking number entry, manual) → order
  status machine → buyer sees tracking number + status history. Refunds:
  seller-initiated or buyer request → admin approve/process/reject. Disputes

7.6 CHAT [LIVE — verified E2E both directions]

9. PAYMENT INTEGRATION — OPTION B (LICENSED-PSP SPLIT) — ARCHITECTURE
--------------------------------------------------------------------------------
DECISION (user-approved, implemented in code as semantics + gating):
  Buyer pays ONCE per checkout → a licensed Malaysian PSP collects the funds,
  deducts the platform's application fee (= commission) AT PAYMENT TIME, and
  settles each seller their share. NOMOFEE NEVER TAKES CUSTODY OF BUYER FUNDS.
  The T+N settlement delay is the PSP's seller-settlement policy + the
  platform's refund policy window.

WHY (rationale preserved in src/lib/psp.ts header):
  * No custody → outside BNM Merchant Acquiring Services registration scope
    (FSA 2013 s.17), no e-money issuance, no MSB/money-broking licence.
  * Commission is force-collected at payment time (no receivables chasing).
  * Multi-seller single payment preserved (PSP split rails).

CODE ARTIFACTS [LIVE]:
  * src/lib/psp.ts — PspProvider interface + PSP_PROVIDERS registry:
      - "mock" (sandboxOnly) — simulates the PSP: PaymentGroup = one PSP
        checkout session; /api/checkout/payments/[ref]/simulate PLAYS the PSP
        and emits the exact webhook a real gateway would send.
      - production candidates documented (DO NOT REMOVE notes):
          stripe_my — Stripe Malaysia + Connect (destination charges,
                      application_fee = commission at payment time) [1st pick]
          curlec    — Curlec marketplace routing (FPX/DuitNow strength)
          ipay88    — iPay88 marketplace product (local method coverage)
    4 documented production plug-in points: (1) implement PspProvider adapter
    and register it; (2) swap simulate endpoint for hosted checkout/redirect;
    (3) point /api/webhooks/payments/[provider] at the real gateway with
    per-provider signature verification; (4) CommissionSetting becomes the
    application-fee configuration.
  * PaymentGroup model = provider-agnostic PSP checkout session record
    (provider stored per checkout) [LIVE].
  * Ledger = ACCOUNTING MIRROR of PSP sub-balances (not custody) [LIVE].
  * PaymentWebhookLog records every webhook for audit [LIVE].

PAYOUTS & SETTLEMENT [LIVE mechanics, config pending]:
  * Wallet pending-hold until T+N → payout batch → bank transfer record.
  * PayoutBatch/Payout + BankAccount admin verification.
  * T+N number is CONFIG (policy), not code.

COMMISSION MODEL [OPEN — deliberately deferred by user]:
  Mechanics fully live (CommissionSetting defaultPercent=8, per-store/category/
  product overrides, fee holidays, simulator, per-line snapshots). The RATE
  MODEL decision (flat %, tiers, category-based, etc.) is deferred — numbers
  are configuration; do NOT hardcode.

PAYMENT COMPLIANCE SUMMARY (Malaysia) — from legal research (worklog Task 7):
  * No BNM licence required for Option B as long as: funds ride a BNM-registered
    acquirer/PSP; platform never holds buyer funds; payouts are ordinary bank
    transfers to Malaysian sellers.
  * E-money licence (FSA 2013) would be triggered ONLY if NOMOFEE issues its
    own withdrawable stored value (NOMOFEE Pay wallet) → wallet is DORMANT
    (§11) until a licensing review.
  * MSBA 2011 remittance licence needed ONLY for cross-border seller payouts —
    not applicable until foreign sellers are onboarded (or partner with a
    licensed remitter/PSP).
  * Consumer Credit Act 2025 (Act 873; SKP regulator; licensing from 1 Jun
    2026) gates any BNPL/pay-later → SPayLater stays DORMANT.
  * Non-redeemable loyalty points (coins redeemable only at checkout) are
    typically limited-purpose and outside e-money regulation — the safe first
    finance feature when revisited.
  * e-Invoice: commission income self-billing + B2C consolidation per MyInvois
    phases (see §8 GAP).
