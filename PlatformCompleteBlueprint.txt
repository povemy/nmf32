## 2. PART A — Executive system inventory

### 2.1 What the product is (plain English)

NOMOFEE (formerly branded SHOPMESH; rebrand completed including DB email sweep via `scripts/rebrand-db.ts`) is a **multi-vendor marketplace platform demo** for the Malaysian market (MYR, en-MY copy): shoppers buy from multiple independent sellers in one cart/checkout; sellers onboard through KYC, run storefronts built with a drag-and-drop page builder, manage products/orders/wallets; admins operate the whole platform (moderation, commission engine, wallets/ledger/payouts, campaigns, support). **Payment is deliberately a sandbox mock** of a licensed-PSP split model (Option B): one buyer charge per checkout, platform commission as the PSP application fee, sellers settled via an internal double-entry ledger and payout batches. Chat is realtime via a tiny socket.io sidecar. Everything runs as **one Next.js app + one SQLite database + one chat micro-service**, behind a single Caddy port.

### 2.3 Major internal modules

`src/lib/money.ts` (POLICY P1 arithmetic) · `commission.ts` (rate resolution + fee holidays) · `ledger.ts` (double-entry T1–T6 + wallet truth) · `psp.ts` (PSP abstraction/scaffold) · `vouchers.ts` · `shipping.ts` (mock courier) · `api.ts` (envelope/audit/notify/transition) · `auth.ts`/`password.ts`/`secretbox.ts` · `marketplaces/*` + `import/*` (catalogue import/claim) · `campaigns.ts` · `sections.ts` (15 builder sections) · `chat.ts` — all cited file:line in the support documents.

### 2.4 Headline architectural conclusions

1. The **financial core is disciplined and centralised** (integer sen/bps, single rounding point, frozen commission snapshots, ledger-derived statements, independent reconcile suite) — but carries **10 ranked residual risks** (Support 06 §H.11), the top being dead admin override config (FIN-01) and non-atomic, status-only-idempotent webhook posting (FIN-02).
2. **Security is demo-grade by intent in payment paths** (hardcoded webhook secret, public simulate) and missing baseline controls elsewhere (rate limiting, CSRF protection with SameSite=None cookies, security headers, git-tracked DB/PII) — 18-item register (Support 07 §K.1).
3. **Marketplace isolation is solid at the request layer** (70/70 admin guards, zero IDOR found in store/me routes, portal escalation blocked) while DB-level constraints are minimal (SQLite reality).
4. **Operational completeness gaps**: no real notifications, no background jobs, no backups, no CI, unwired endpoints, one broken admin button — all catalogued with evidence (Support 10).

## PART B — Complete repository and file map

### B.1 Application shape (plain English first)

NOMOFEE is a **single Next.js 16 application** (App Router, Turbopack dev) that contains three logically separate products — a shopper marketplace, a seller portal and an admin back office — mounted as **client-side view machines on the single user-visible route `/`** (`src/app/page.tsx:1-5` → `src/components/app-root.tsx:14-46`). All server logic lives in ~120 API route handlers under `src/app/api/**`; there are **no server actions** (zero `'use server'` matches) and no RSC data fetching. A second, deliberately tiny process (`mini-services/chat-service`, socket.io on :3003) relays chat messages. Persistence is one SQLite file via Prisma. A Caddy gateway (:81) is the only externally exposed port and forwards `?XTransformPort=` requests to internal services. [V]

The codebase grew task-by-task under an orchestrator/worklog regime (Tasks 1–19 per `worklog.md`); layering is clean in the API layer but the frontend contains several very large multi-concern client files (see hotspots in Support 10).

### C.2 Communication paths (verified)

1. **Browser → frontend**: one SSR'd shell page; everything after load is client state machines. Deep links honoured: `?sf={store}&sp={product}` (SEO/sitemap contract, `shopper-shell.tsx:163-170`) and `?claim_job=&claim_token=` (import claim, :153-162). [V]
2. **Frontend → backend**: `fetch('/api/…')` with per-portal helpers — shopper `fetchJson/postJson` attaches **device headers only** (`X-Cart-Token`, `X-Shopper-Token`; cookie does session) (`shopper/ui-bits.tsx:214-276`); seller `withAuth` adds `Authorization: Bearer` (`seller/ui-bits.tsx:98-126`); admin `use-api.ts` adds Bearer. Session validation is server-side dual-channel: Bearer header **or** `sm_session` cookie (`src/lib/auth.ts:53-76`). [V]
3. **Backend → services**: route handlers import `src/lib` directly; `src/lib` imports `db.ts` (Prisma). No service layer between routes and lib; no DI. [V]
4. **Backend → database**: Prisma Client (singleton, global-cached in dev, `db.ts:13`), SQLite file, journal_mode=delete, foreign_keys enforced by Prisma per-session. `$transaction` used in only **7 route files** (checkout/create, auth/register, claim/bind, checkout/addresses ×2, store/inventory/adjust, store/collections/[id]/products). [V]
5. **Realtime**: Next API persists `ChatMessage` then POSTs `http://127.0.0.1:3103/broadcast {room:"thread:<id>", event:"chat:message"}` (`src/lib/chat.ts:7-20`, 1.5s timeout, failure non-fatal); hub emits to room. Clients `io("/?XTransformPort=3003")`. **No auth on socket join** (rooms are client-claimable; risk R-RT1 in Support 07). [V]
6. **Asynchronous processing**: **none exists**. Simulated workers: `dispatchStoreWebhooks` writes success rows without network calls (`src/lib/api.ts:127-144`); notifications are inline `NotificationLog` rows (`api.ts:113-124`); mock shipments advance lazily on buyer order reads (45s guard, `me/orders/route.ts:146`) or via uncalled `POST /api/shipping/tick`. 7. **File/image storage**: local `public/` only; import copier writes `public/uploads/{storeId}/{sha256-16}.{ext}` with SSRF-guarded fetch (`src/lib/import/runner.ts:52-77`); no S3/OSS. Image "generation" = deterministic SVG service `/api/img/{seed}` + client-side seed reshuffling. [V]

## E.3 End-to-end trace A — checkout → paid order → ledger

1. **Quote** `POST /checkout/quote` (`quote/route.ts`): `priceItems` (server price from variants; qty/active/live validation) → `computeGroupPricing` (per-store groups, per-group free-ship threshold RM100 standard/express RM15 non-East-MY, coupon applies to exactly ONE highest-subtotal eligible group) → `buildVoucherOutcomes` soft mode → aggregate. Nothing persisted. [V] `checkout/pricing.ts:12-17,78-330`
2. **Create** `POST /checkout/create` (`create/route.ts`): requireShopper → **replay by idemKey** (PaymentGroup then legacy Order; 403 cross-user) → validation (provider ∈ KNOWN_PROVIDERS, address, email/phone) → **recompute pricing from scratch** → **hard voucher mode** (unusable selection ⇒ 409) → commission via `computeOrderCommissions` on voucher-adjusted totals → `nextOrderNumber()` per group (**outside tx**) → **single `$transaction`**: stock re-check (check-then-act decrement, no `stock >= qty` conditional), PaymentGroup, Orders(payment_pending), **atomic voucher redemption** (guarded `updateMany AVAILABLE→USED` + quota increment), OrderItem.createMany **with frozen commission snapshots**, stock decrement + InventoryLog + salesCount, history row, CouponRedemption+timesUsed → post-commit notify+audit. [V] `:33-350`
3. **Pay** `GET /payments/[ref]` (public status; computed `expired`), **simulate** (server signs payload with `WEBHOOK_SECRET` and calls the exact production processor), **retry** (failed→requires_payment). [V]
4. **Webhook** `POST /webhooks/payments/[provider]` → `processPaymentWebhook` (`webhooks/payments/process.ts`): always log `PaymentWebhookLog` first (incl. bad signatures) → HMAC-SHA256 over `"{ref}.{event}.{amountMinor}.{ts}"`, **hardcoded demo secret** (`:26`), non-timing-safe compare (`:63`), **no replay window** → amount guard 409 → **duplicate handling = status check** (`group.status==="succeeded"` ⇒ no-op `duplicate:true`, `:98-110`; intent `:210-221`) → success: `group.succeeded` → per order `transitionOrder(→paid)` → **T1** `postOrderPaid` (DR GATEWAY total / CR SELLER:PAYABLE net w/ `availableAt=holdUntil` / CR REVENUE_COMMISSION) + `refreshWalletCache` → simulated store webhooks + notifications + **cart cleared server-side**. [V]
5. **Known hazards** (detailed in Support 06): non-transactional success path (status flip before ledger; crash ⇒ paid order never credited, retries return duplicate), status-only idempotency ⇒ TOCTOU double-T1 under concurrency, T1 silently skipped if seller/wallet missing (`:151,268`). [V]

## E.5 Trace B — refunds; Trace C — payouts (summaries; full detail Support 06 §5–6)

**Refunds**: shopper `return-request` creates a **Dispute** (no money); seller `refund-request` is the **only `db.refund.create`** (amount ≤ total−Σnon-rejected); admin approve/reject; **process** = Refund(processed) + `commissionReversalMinor = bpsOf(amount, frozen item bps)` + **T5** + order→`partially_refunded|refunded` + OrderItem.refundedMinor (whole amount charged to first item with remaining balance — heuristic) + restock (**full item qty regardless of partial amount**) + paymentIntent→refunded. **No `$transaction`**; idempotency = status check-then-act. [V]

**Payouts**: `POST /admin/payout-batches {dryRun}` → eligibility = ledger-truth `availableMinor ≥ payout.min_minor` → real run: batch(running) → per wallet: counter `PO-<n>`, statement period since last **paid** payout, `buildLedgerStatementFromLedger` (ledger-derived, balancing "retained" line), Payout(processing) + **T3**; batch→completed. `mark-paid` ⇒ **T4** (clearing→bank) + paidAt/providerRef; `fail` ⇒ **T4f** (reverse to payable, immediately available). Non-transactional loop; small check-then-act races. [V]

## E.6 Cross-cutting anomalies

- **Uncalled endpoints**: `GET /api/store/payouts`, `/api/admin/announcements*`, `/api/admin/webhook-deliveries(+replay)`, `POST /api/shipping/tick`. **Broken caller**: `admin/stores.tsx:64` → non-existent `/api/admin/domains/[id]/verify` (404). [V]

- **Unauthenticated mutation surface**: simulate, retry, webhook, reviews, newsletter, shipping/tick, import jobs — all flagged in Support 07 §5.

## F.1 Overview

- **76 models, 0 enums** (SQLite+Prisma: enums are Strings + app-level validation). IDs: `String @id @default(cuid())` except `CommissionSetting.id Int` and `Counter.key String`. # Blueprint Support 06 — Financial Engine & Money Precision (Part H) + Financial Integrity Map (Part V)

The most audit-critical document in this blueprint. Labels [V]/[I]/[P]. Key claims cross-verified by direct reads of `src/lib/money.ts`, `src/lib/commission.ts`, `src/lib/psp.ts`, `prisma/schema.prisma` and the live DB snapshot (Support 04 §F.1).

## H.1 Money & rate primitives — POLICY P1 (`src/lib/money.ts:1-118`)

One documented policy governs every module [V]:

1. **Storage**: integer minor units (sen) for money; integer bps for rates (`BPS_DENOM = 10_000`, `money.ts:53`; derived `BPS_PER_PERCENT_POINT`, `BPS_DECIMALS` — scale raise to 1,000,000 is a documented one-line change). No FLOAT/DOUBLE money columns remain (only `Product.ratingAvg Float`, non-money, and `FinMigrationBackup.oldValue Float`, audit anchor).
2. **Rounding**: exactly ONE rounding point per payable amount — **ROUND_HALF_UP away from zero on exact integer arithmetic** (`divHalfUp`/`mulDivRoundHalfUp` with automatic BigInt beyond `MAX_SAFE_INTEGER/2`); never `Math.round(a/b)`, never `toFixed` on money.
3. **Splits**: largest-remainder allocation (`allocateProportionally`) — Σ(parts) ≡ amount exactly, deterministic tie-break.
4. **Nets**: pure integer add/sub of already-rounded amounts.
5. **Overflow**: BigInt fallback paths; `assertSafeInt` throws `MONEY_INT_VIOLATION`.
6. **Display**: formatting divides for presentation only, never feeds back.
7. **Input**: digit-exact parsing (`parsePercentToBps` "8.35"→835; >2dp **rejected**, not rounded); legacy shim `percentToBpsExact` flags lossy values.

**Commission engine** (`src/lib/commission.ts`): settings singleton (`defaultBps` 800, `appliesToShipping` false, `basePriceRule paid_price`, `fixedFeeMinor`, `minCommissionMinor`, `payoutHoldDays` 7, hold rules) → `resolveRate` chain **CommissionOverride table row → product → nearest category ancestor (cycle-guarded) → seller → global**, then an active fee holiday **replaces** the rate (clamped ≤ normal); per-line `base = lineSubtotal − discount` (+ shipping only when `appliesToShipping`); `percentPart = bpsOf(base, rate)` (`:286` — the single rounding point); `commission = percentPart + fixedFeeAlloc`; `sellerNet = base + shippingAlloc − commission` (`:288`); per-order min-commission floor (skipped on any holiday, `:319-332`); results snapshotted per line (`commissionBps` + `breakdownJson`) **and never recomputed**.

**CommissionOverride table — fee/hold semantics (FIN-01 R1, 2026-10-18)** [V]: the TABLE winner (specificity product 3 > category 2 > seller 1; ties by latest validFrom then createdAt) applies **ALL of its non-null fields**, not just `bps`: `bps` → rate (source `override`); `fixedFeeMinor` → the per-order fixed fee; `holdDays` → the payout hold, **winning over the static `Seller.holdDaysOverride`** (step 4 beats step 0 — a time-boxed admin tool beats coarse columns). A `bps=null` row with fee/hold set is therefore NOT dead. Validation mirrors `applyFeeHoliday` (`applyOverrideFields`): a stored `fixedFeeMinor` outside [0, MONEY_INT_MAX] or `holdDays` outside [0, 3650] (only possible via direct DB edits — the admin API rejects them with 400s) is **IGNORED** with flags `invalid_override_fixed_fee_ignored:<rowId>` / `invalid_override_hold_days_ignored:<rowId>`; a valid value that actually CHANGES a field adds `override_fixed_fee_applied` / `override_hold_days_applied` to the frozen snapshot. **First-item convention**: the fixed fee is a per-order quantity allocated proportionally across items, so `computeOrderCommissions` takes it from `rates[0]` (same convention as `holdDays`) — scope fee/hold overrides at seller/category level for multi-item predictability. **Fee holidays are rate promotions only**: the holiday branch returns `{...normal, bps}` so override-sourced fee/hold survive a holiday. The resolved `holdDays` is frozen onto **`Order.holdDays` at checkout** and the payment webhook posts T1 with `order.holdDays ?? seller.holdDaysOverride ?? global` — the ledger hold equals the hold quoted at checkout (null = legacy order → old fallback).

## H.3 Fee holidays — semantics verdict [V]

**`FeeHoliday.bps` = the commission RATE CHARGED during the window (bps of order base); 0 = full waiver; a partial holiday is APPLIED, not a full waiver.** Established from converging evidence (not assumed):

1. Engine (authoritative): `commission.ts:79-92` `applyFeeHoliday` — invalid rate (non-safe-int, <0, >10,000) ⇒ holiday **ignored** with flag `invalid_fee_holiday_ignored:<id>`; `holidayBps > normalBps` ⇒ clamped to normal with flag `holiday_rate_above_normal`; otherwise `bps = holidayBps`. Header `commission.ts:10-35` documents the semantics rationale ("the 'percentage waived' reading is ruled out because it contradicts '0 = full fee holiday'").
2. Schema comment `schema.prisma:76`: "informational holiday rate in bps (**0 = full fee holiday**)".
3. Seed `seed.ts:490-497`: "0% for a week" → `bps: 0`.
4. Admin UI hint (`finance.tsx:576-578`): "**Commission % during holiday** · 0 = full fee holiday · e.g. 5 charges 5% commission during the window".
5. E2E script `scripts/e2e-fin-issues.sh:21-29`: 300bps ⇒ RM120.00 × 3% = 360 sen exact.

Operational rules [V]: window test inclusive both ends (`startsAt ≤ now ≤ endsAt`, `:167`); overlaps allowed — **earliest-starting matching holiday wins** (`orderBy startsAt asc`, first match, `:166-175`); scheduled/expired/disabled excluded by the where clause; **rate fixed at order creation** (frozen snapshot; no retroactive change; refunds reverse from frozen bps); min-commission floor skipped for the whole order under any holiday (`:319`). Timezone: UTC server-time comparisons; no MYT normalisation [P].

✅ **Documentation drift (FIN-07) — RESOLVED 2025-10-18 (post-blueprint fix round)**: the stale comments at `schema.prisma:77` and `admin/commission/holidays/route.ts:30-32` ("the engine currently grants a FULL holiday (rate→0) when active") have been corrected to describe the actual charged-rate semantics. Engine code was NOT modified — it was already correct. Resolution evidence: `fin-tests.ts` **56/56 passed** (section 9 fee-holiday semantics: partial rate applied, clamped ≤ normal, invalid ignored + flagged) and `fin-reconcile.ts` **25/25 passed** (section K re-derives holiday snapshots from the configured charged rate) — both executed during the fix round. The earlier external warning that "the calculation engine always grants a full waiver" applied to pre-M-FIN-1 behaviour / the stale comments, not to the current engine.

## H.4 Ledger architecture (`src/lib/ledger.ts`)

- **Accounts** (`:17-31`): `PLATFORM:BANK_MAIN` (asset), `PLATFORM:PAYOUT_CLEARING` (liability), `PLATFORM:REVENUE_COMMISSION`, `PLATFORM:REVENUE_ADJUST` (revenue), `GATEWAY:{provider}` (asset), `SELLER:{walletId}:PAYABLE` (liability, wallet-linked). Sign convention: wallet balance = Σcredit − Σdebit on PAYABLE.
- **Posting helper** `postTransaction` (`:59-94`): computes debit/credit sums, **throws `LEDGER_UNBALANCED` pre-write** if unbalanced or zero; txn+lines atomic via nested create; `ensureAccount` upserts; **no idempotency key** (no DB unique on `(txnType, refType, refId)`).
- **Postings lifecycle** [V]: **T1** `postOrderPaid` (webhook success): DR GATEWAY total / CR SELLER:PAYABLE net (`availableAt = paidAt + holdDays`) / CR REVENUE_COMMISSION → `refreshWalletCache`. **T2** `postGatewaySettlement` (bank↔gateway; no runtime caller — seed only). **T3** `postPayoutInitiated`: payable→clearing. **T4** `postPayoutConfirmed`: clearing→bank. **T4f** `postPayoutFailed`: reversal to payable (`availableAt=now`). **T5** `postRefund`: DR payable (seller share) + DR commission (reversal) / CR gateway. **T6** `postAdminAdjustment`: payable ↔ REVENUE_ADJUST.
- **Wallet truth** `walletTruth` (`:106-134`): pending = credits with `availableAt > now`; available = matured credits − debits (**can go negative** — no floor); denormalised into `Wallet` cache columns **on every write**; drift detectable via `runLedgerInvariants` (`:303-320`) — invoked only by `/api/health` and `/api/admin/system/health` (**no scheduler despite "nightly" comment**, `ledger.ts:302`).

## H.5 Wallets, earnings, payouts

- **Seller wallet reads** (`store/wallet/route.ts:12-28`): truth-refreshed wallet + last 20 PAYABLE lines + payouts; full journal drill-down ownership-checked. **Buyer wallet dormant**: `me/wallet` returns `disabled:true` envelope; coins claim 403 `FEATURE_DORMANT` (`NOMO_FINANCE_ENABLED=false`); seller-payout wallet explicitly outside the flag (`feature-flags.ts:26-30`).

## H.7 PSP layer & webhook idempotency (`src/lib/psp.ts`, `webhooks/payments/process.ts`) [V]

- **Option B (licensed-PSP split) is the documented model** (`psp.ts:1-36`): buyer pays once per checkout; a licensed PSP collects, deducts commission as application fee, settles sellers; **platform never takes custody** (FSA 2013 s.17 note). Sandbox has only `mock` ("NomoPay Checkout (sandbox)"); `PaymentGroup` = one PSP session; the **4 production plug-in points** are: (1) implement+register `PspProvider`, (2) replace simulate with hosted checkout, (3) point the webhook route at the real gateway with per-provider verification, (4) `PaymentGroup.provider` already stores the provider id; commission rate becomes the application fee. Candidates `stripe_my`/`curlec`/`ipay88` are documented stubs with `awaitingAdapter: true` (`PSP_SPLIT_CANDIDATES`, `:87-92`); `psp-settings` PUT `autoSettle:true` is **hard-blocked 409 `PSP_ADAPTER_REQUIRED`**. T2 `postGatewaySettlement` exists for the future settlement mirror.
- **Webhook verification**: HMAC-SHA256 hex over `"{ref}.{event}.{amountMinor}.{ts}"`; **secret hardcoded in source** (`process.ts:26`, demo value; production swap is a documented plug-in point but nothing enforces it); signature from header or body; **plain `===` compare** (`:63`); **no timestamp freshness check**. Every delivery logged to `PaymentWebhookLog` (log-first, incl. invalid signatures).
- **Idempotency = status check**: succeeded group/intent ⇒ no-op `duplicate:true` (`:98-110`, `:210-221`); second delivery creates one more log row only. Amount guard 409. **Not DB-enforced** (no unique on refType/refId) and the success path is **not transactional**: status flips **before** T1 ⇒ crash window = paid order never credited (retries return duplicate); concurrency ⇒ TOCTOU double-T1; T1 silently skipped if seller/wallet missing (`:151`, `:268`). Policed post-hoc by reconcile section M (order_paid postings ↔ paidAt 1:1).
- **P1 race hardening (2025-10-18)** — the two bullets above describe the **pre-P0** state and are superseded by the FIN-02 register row: P0-1 rewired verification (env `PAYMENT_WEBHOOK_SECRET` + timing-safe compare + 15-min replay window) and made success paths ONE `$transaction` with DB-enforced idempotency (P2002 → `duplicate:true`). Evidence: `scripts/fin-concurrency.ts` live race suite — 8-way simulate race + mixed webhook/simulate race → ALL HTTP 200 with graceful duplicates, **exactly ONE `order_paid` per order**, ledger balanced; payout double-race → `PAYOUT_RACE` guard fired, losing batch failed cleanly, zero orphan T3s.

- **Passwords** [V]: scrypt (`scryptSync`, 64-byte key, random 16-byte salt, `s1:salt:hash`), `timingSafeEqual` compare (`lib/password.ts:4-20`).
- **Sessions** [V]: DB `Session` row, token = 32-byte CSPRNG hex (`randomToken(32)`), fixed 7-day TTL, DB-revocable; cookie `sm_session`: `httpOnly, SameSite=None, Secure, path=/, maxAge=604800` (`lib/auth.ts`). **Stored sha256-hashed at rest (F-09, P1)**: `Session.token` = hex(sha256(raw)); every lookup goes through the hash-first `getSessionByToken()` helper — live-verified (lookup by raw finds nothing; digest-as-Bearer rejected). **Rotated + revocable since Task 22-b (R2, 2025-10-18)**: `rotateSession()` retires the presented token (cookie or Bearer, delete-first so the old token dies immediately) and issues a fresh one for the same principal — wired at `POST /api/me/password` (live proof: old token → 401 on guarded routes / `userType:null` on the session probe, new token → 200, DB row count for the old digest = 0); `revokeUserSessions(userType, userId)` deletes every live session for a principal and is wired on admin seller **suspend / terminate / reject** (audit `after.sessionsRevoked`) — live proofs: approved-then-suspended seller's Bearer token 401s immediately, terminated/rejected likewise, suspended re-login → `403 ACCOUNT_SUSPENDED`, terminated → `403 ACCOUNT_TERMINATED`. ## R5 ADDENDUM — real-PSP adapter scaffold (Task 22-c)

Additive, env-gated scaffold so a licensed gateway can be dropped in without touching the mock
or `webhooks/payments/process.ts`. With no `STRIPE_*` env keys the sandbox behaviour is
byte-identical to pre-R5 (fin-tests green, mock simulate/webhook/live E2E unchanged).

**Adapter interface extension** (`src/lib/psp.ts`):

- `PspProvider` gains a REQUIRED `isConfigured(): boolean` (env gate, read at call time, secrets
  never hardcoded; mock ⇒ `true`) and two OPTIONAL capabilities with documented contracts:
  - `createCheckoutSession?(input): Promise<{redirectUrl, providerRef}>` — hosted checkout
    (toggle point 2). CONTRACT: use only server-computed numbers; stamp the canonical internal
    ref (`input.groupRef` = `PaymentGroup.ref`) onto the remote session (metadata) and ECHO it
    back as `providerRef` so the adapter's own webhook verifier reports a resolvable ref; be
    idempotent per groupRef; throw typed `PspAdapterError("PSP_NOT_CONFIGURED")` instead of
    calling the network unconfigured. Input carries the Option B split (group amount, currency,
    `commissionMinor` application-fee total, per-seller `{sellerId, amountMinor,
    commissionMinor, pspAccountId?}` lines).
  - `verifyWebhookSignature?(req, rawBody): Promise<PspWebhookVerdict>` — native verification
    (toggle point 3). CONTRACT: constant-time compare only; NEVER trust unverified body fields
    (parse only after the compare); enforce a replay window; return `{valid, providerRef?,
    eventId?}` plus OPTIONAL normalized fields (`eventType` in the internal
    `payment.succeeded|payment.failed` vocabulary, `amountMinor`, `ts`) so the dispatch route
    can run the unchanged pipeline.
- New typed error `PspAdapterError(status, code, message)`; routes convert it to the standard
  error envelope.

**Lazy registry** (`src/lib/psp.ts` — the static `PSP_PROVIDERS` + `PSP_SPLIT_CANDIDATES` + the 4
plug-in-point notes stay intact): `getPspProvider(id)` returns the adapter from
`PSP_LAZY_ADAPTERS` ONLY while `isConfigured()`, else falls back to the static map (mock for
unknown ids). `getPspProviderForMethod(method)` maps the checkout payment METHOD
(`card_stripe → stripe_my`; Curlec/iPay88 pending) to its adapter. The static-only
`resolvePspProvider` (used by the `/simulate` gate) is deliberately untouched.

**`src/lib/psp-adapters/stripe-my.ts`** — Stripe Malaysia + Connect skeleton (NO SDK, raw
fetch; never executes in this sandbox):

- Env: `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` (both required; `sandboxOnly` getter is
  `false` exactly when both are present, `true` otherwise).
- `createCheckoutSession`: `POST /v1/checkout/sessions` form-encoded — `mode=payment`, one line
  item for the whole group, `payment_intent_data[transfer_group]` = canonical group ref,
  `metadata[nomo_ref]` + `client_reference_id` stamping, Stripe `Idempotency-Key:
  checkout:<groupRef>`; when exactly ONE seller with a known `pspAccountId` → destination
  charge with `payment_intent_data[application_fee_amount]` = commission (the Option B note
  verbatim); otherwise separate-charges-and-transfers (platform retains commission, per-seller
  Transfers issued on webhook confirmation — production follow-up: `Seller.pspAccountId`
  column + Transfer issuance). `PSP_NOT_CONFIGURED` guard before any fetch.
- `verifyWebhookSignature`: the real Stripe scheme — `stripe-signature: t=…,v1=…` header,
  HMAC-SHA256 over `` `${t}.${rawBody}` ``, every v1 candidate compared constant-time
  (reuses `safeEqualHex` → `timingSafeEqual`), 5-minute replay tolerance, body parsed only
  after the compare; maps `checkout.session.completed`/`async_payment_succeeded`/
  `payment_intent.succeeded` → `payment.succeeded` and
  `checkout.session.expired`/`payment_intent.payment_failed`/`charge.failed` →
  `payment.failed`; returns `providerRef` from `metadata[nomo_ref]` →
  `client_reference_id` → object id, `amountMinor` from `amount_total`/`amount`, `ts` from the
  authenticated signing timestamp. Proven offline (Task 22-c: 16/16 cases — valid, uppercase
  hex, tampered, stale 6 min, fresh 4 min, wrong secret, missing header, body-swap,
  unconfigured throws, registry/sandboxOnly gating).

**Per-provider webhook dispatch** (`webhooks/payments/[provider]/route.ts`, additive branch at
the top; the mock branch below it is byte-identical — only the import line and header comment
grew): if `[provider]` resolves to an adapter with `verifyWebhookSignature`, the adapter
verifies first; invalid → log-first (`PaymentWebhookLog signatureValid=0`, unverified body
fields NOT parsed out) then 400 `BAD_SIGNATURE`; valid-but-unmapped event types → 200
`{ignored:true}` (no PSP retry storm); valid + normalized → the route re-signs the normalized
internal event with the platform's `PAYMENT_WEBHOOK_SECRET` (never leaves the server) and calls
the UNCHANGED `processPaymentWebhook` with the RAW PSP body preserved as the log payload — so
the 15-min replay window, atomic T1, DB-enforced idempotency and fan-out apply to real gateways
exactly as to the mock.

**Checkout hook** (`checkout/create/route.ts`, single additive branch where the payment ref is
built): when the method's adapter exposes `createCheckoutSession` and is configured, the
adapter's `redirectUrl`/`providerRef` replace the mock `/pay/{ref}` default; adapter errors
surface as `PSP_NOT_CONFIGURED` / `PSP_UPSTREAM_ERROR` / `PSP_SESSION_FAILED`. Unconfigured →
byte-identical mock flow. Note: the SPA still navigates by `orderPaymentRef` (client-side pay
