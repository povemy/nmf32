# MASTER INSTRUCTION: REVAMP AND FULLY CONNECT THE ANDROID E-COMMERCE CHECKOUT SYSTEM

## 1. PRIMARY OBJECTIVE

Revamp the existing Android application's entire e-commerce checkout experience into a modern, reliable, Shopify-inspired, three-phase checkout system.

This is not merely a UI redesign. It is a full checkout-flow improvement and functionality-integration task.

The objective is to transform the existing checkout system into a complete, functional, end-to-end shopping experience in which every relevant button, component, feature, action, state transition, API call, database operation, and checkout-related business rule is properly connected and operational.

Currently, many functions and features in the application appear to be hardcoded, partially implemented, simulated, disconnected, or not connected to their intended backend functionality. Investigate the existing implementation and resolve these issues systematically.

You must work with the actual codebase, existing architecture, current database structure, existing APIs, authentication system, business logic, and available integrations. Do not invent an entirely new architecture when the existing implementation can be improved.

Treat this as a functional engineering task that includes UI, state management, backend integration, data persistence, validation, error handling, security, and testing.

### Core goals

1. Introduce a clear three-phase checkout experience inspired by Shopify.
2. Make the checkout responsive, intuitive, consistent, and suitable for an Android e-commerce application.
3. Connect all checkout components to real application state and appropriate backend operations.
4. Identify and remove inappropriate hardcoded or mocked production behavior.
5. Ensure customer, address, delivery, cart, pricing, discount, payment, and order data remain consistent throughout checkout.
6. Ensure every relevant action has a defined and working outcome.
7. Prevent incomplete, duplicate, inconsistent, or invalid orders.
8. Connect the checkout to the existing product catalog, cart, user account, inventory, payment infrastructure, and order management system wherever those capabilities already exist.
9. Preserve existing working functionality and integrations.
10. Verify that the complete customer journey works, rather than considering the task complete when the screen looks correct.

Do not assume a specific technology stack, framework, payment provider, database, or backend platform. Inspect the project and adapt the implementation to what actually exists.

## 3. IMPLEMENT A THREE-PHASE CHECKOUT FLOW

Create a Shopify-inspired checkout experience with three distinct phases.

The interface should make it immediately clear which phase the customer is in, what information is required, what has already been completed, and what action is needed next.

Use a clear progress indicator with three labeled stages:

1. Information
2. Delivery
3. Payment

Use the terminology that best fits the application's existing language and product context, while retaining the three-phase structure.

### Global checkout behavior

The three phases must form one continuous checkout process rather than three independent screens with unrelated state.

The checkout should maintain a consistent view of the current cart, calculated totals, customer details, selected address, delivery option, discount information, and applicable fees.

Implement appropriate navigation between phases.

Customers should be able to return to a previous phase to correct their information without unnecessarily losing valid data already entered.

Moving forward must perform the appropriate validation before allowing the next phase to open.

Do not allow a customer to skip required steps simply by navigating directly to a later screen.

Preserve checkout state appropriately during normal screen transitions, configuration changes, and temporary interruptions. Persist sensitive or transaction-critical information only through appropriate mechanisms.

### PHASE 1: INFORMATION

This phase collects and verifies the information needed to prepare the order.

Inspect the existing customer and account functionality and reuse it wherever practical.

Depending on the capabilities supported by the application, this phase should cover:

- Customer name.
- Email address or other required contact information.
- Phone number, when required.
- Recipient information, where different from the account holder.
- Delivery address selection.
- Existing saved customer addresses.
- Adding a new address.
- Editing an existing address.
- Selecting a default address when appropriate.
- Any additional fields required by the application's actual fulfillment process.

For guest checkout, support it only if the application's current business rules and backend architecture permit it. Do not introduce guest checkout simply by bypassing existing authentication requirements.

#### Functional requirements

- Populate available customer information from the appropriate source.
- Allow customers to modify editable fields.
- Validate required fields and applicable formats.
- Display useful, field-specific validation messages.
- Save address changes through the correct persistence mechanism when appropriate.
- Ensure the selected address is associated with the correct customer or permitted guest session.
- Preserve entered information when navigating backward and forward.
- Clearly indicate loading, save failures, and other relevant states.
- Prevent progression when mandatory information is invalid or missing.

When the customer continues, carry the validated information into the shared checkout state and proceed to Phase 2.

Do not make the Continue button navigate to the next phase without validating and retaining the required data.

### PHASE 2: DELIVERY

This phase handles the delivery or fulfillment details for the current order.

Inspect the existing shipping, vendor fulfillment, pickup, and delivery implementations before deciding how to present the available options.

Use only delivery methods that the application can genuinely support.

Depending on the current business model, available options may include:

- Standard delivery.
- Express delivery.
- Other supported shipping methods.
- Store or vendor pickup.
- Collection or other supported fulfillment arrangements.

Do not display delivery methods that are merely decorative or unavailable to the actual order fulfillment system.

#### Functional requirements

- Retrieve or calculate available delivery options using the appropriate source.
- Determine eligibility based on the delivery address, cart contents, vendor restrictions, inventory, order value, location, or other applicable business rules.
- Display actual shipping fees where supported.
- Allow the customer to select an available delivery option.
- Update the shared checkout state when the selection changes.
- Recalculate the order total whenever delivery charges change.
- Handle unavailable shipping methods and invalid address combinations.
- Request address correction when a destination cannot be served.
- Retain the chosen delivery option when navigating between phases, provided it remains valid.
- Revalidate availability and cost before order submission when necessary.
- Support separate fulfillment arrangements for multi-vendor carts if the existing architecture requires them.

If delivery fees depend on external services, vendor rules, or backend calculations, connect to the existing integration rather than hardcoding prices into the UI.

The customer must be able to understand the selected fulfillment method and its associated charges before proceeding.

When the customer continues, validate the selection and proceed to Phase 3.

### PHASE 3: PAYMENT AND ORDER REVIEW

This phase presents a final order review and allows the customer to complete payment using the payment methods genuinely supported by the application.

The customer should see a clear summary of the information relevant to the final purchase.

Where applicable, include:

- Products and selected variants.
- Product images.
- Product names and relevant item options.
- Individual item prices.
- Quantities.
- Subtotals.
- Discounts and applied vouchers.
- Delivery charges.
- Taxes and additional fees.
- The selected delivery method.
- The delivery address or collection details.
- The final payable amount.
- Available payment methods.
- Relevant order terms and required acknowledgements.

The exact displayed fields should follow the application's existing data model and business requirements.

#### Payment functionality

Investigate the existing payment integration before modifying the flow.

Use the supported payment provider or payment backend that already exists. If multiple methods are supported, connect each eligible method to its corresponding real payment flow.

Requirements:

- Display only payment methods that are genuinely available.
- Handle payment-method selection and any required validation.
- Initiate payment through the correct provider integration or backend endpoint.
- Handle authentication challenges, redirects, callbacks, cancellations, and failures as required by the provider.
- Verify payment status through a trusted backend or provider-authoritative mechanism.
- Prevent the UI from treating an unverified payment response as proof of successful payment.
- Prevent repeated taps or retry operations from generating unintended duplicate transactions.
- Clearly communicate payment processing, success, cancellation, failure, and pending states.
- Provide a safe retry or recovery path when supported.
- Reconcile the final payment result with the application's order status.

Never simulate a real successful payment in the production checkout flow.

If production payment credentials or a required provider integration are unavailable, implement the appropriate integration boundary and clearly identify the missing configuration. Do not claim the payment process is fully functional until it has been verified.

#### Final order submission

When the customer confirms the order, execute the correct order submission workflow.

Before accepting the order, ensure the backend or trusted transaction-processing layer validates the necessary information, including:

- Current product and variant availability.
- Valid quantities.
- Authoritative product prices.
- Applicable discounts and pricing rules.
- Delivery eligibility and charges.
- Applicable taxes and fees.
- The final payable amount.
- Customer and delivery information.
- Payment requirements.
- Any additional business rules required by the existing application.

Do not trust the final amount, discount, stock availability, or other financially significant information supplied only by the Android client.

Use the backend as the source of truth wherever the existing architecture permits.

Implement appropriate transactional behavior, idempotency, and order/payment state management according to the existing backend capabilities.

Do not create duplicate orders when a user taps the confirmation button repeatedly, refreshes the screen, retries an uncertain request, or returns from a payment provider.

After processing, display a clear and accurate result based on the actual order and payment status.

## 4. COMPLETE THE ENTIRE CHECKOUT LIFECYCLE

The checkout must not end at the payment screen.

Trace and connect the complete customer journey:

Product discovery → Product details → Add to cart → Cart management → Checkout → Information → Delivery → Payment and review → Order creation → Payment reconciliation → Order confirmation → Order history → Order details.

Use the corresponding existing screens and services where available.

### Cart integration

Ensure the checkout receives the correct current cart contents.

Verify that:

- Adding an item from a product screen updates the cart.
- Changing item quantities updates the correct cart item.
- Removing an item removes it from the applicable cart.
- Product variants and options are retained correctly.
- Cart quantities and availability are validated.
- Cart totals update when the underlying items or quantities change.
- The checkout reflects relevant cart changes instead of relying on stale, independently maintained data.
- Empty carts cannot proceed to checkout.
- Invalid cart states are handled gracefully.
- The cart is updated or cleared after successful order creation according to the existing business rules.

Do not assume that a successful navigation event means the cart operation has actually succeeded.

### Order integration

Verify that successful checkout creates the appropriate order records through the actual order management system.

Where applicable, confirm that:

- The order is linked to the correct customer.
- The purchased items and quantities are recorded correctly.
- The agreed delivery information is retained.
- Monetary totals and pricing breakdowns are consistent.
- Payment and order statuses are tracked independently where necessary.
- Vendor-specific order records or fulfillment records are created when required by the existing architecture.
- Inventory updates follow the intended transaction and reservation rules.
- Order history displays the new order.
- Order detail screens show the actual order information.
- Failed or cancelled payment attempts do not create misleading completed orders.
- The customer receives an accurate confirmation result.

Use the existing order lifecycle and data model unless there is a demonstrable need to change them.

Do not invent new order statuses or change existing status meanings without checking their impact on other application features.

## 5. PROJECT-WIDE FUNCTIONALITY AUDIT: ELIMINATE DISCONNECTED FEATURES

The checkout revamp is also an opportunity to identify and correct broken or disconnected functionality in the existing application.

Audit the code related to checkout and its dependencies rather than focusing only on the three checkout screens.

Inspect relevant UI components, buttons, menus, input fields, dialogs, navigation actions, service calls, repositories, state holders, models, and database interactions.

Look for the following types of problems.

### A. Hardcoded production behavior

Identify values or behaviors that should be derived from application data, configuration, user choices, or backend rules.

Examples include:

- Fixed product prices.
- Hardcoded delivery charges.
- Hardcoded tax or discount values.
- Fake customer details.
- Placeholder order numbers.
- Static shipping methods presented as available without checking eligibility.
- Fake payment success responses.
- Dummy cart contents.
- Hardcoded order status.
- Fixed inventory quantities.
- Static addresses presented as persisted customer addresses.
- Mock API responses used in production paths.
- Placeholder values that never update when the underlying data changes.

Replace such behavior with the correct existing data source, calculation, integration, or configuration.

However, not every hardcoded value is wrong. UI labels, design constants, enum definitions, default presentation values, and intentional static configuration may legitimately remain hardcoded.

Use engineering judgment. The goal is to eliminate incorrect hardcoded business behavior, not mechanically remove all constants from the project.

### B. Disconnected buttons and actions

Inspect every checkout-related button and interaction.

Examples include:

- Add to cart.
- Increase or decrease quantity.
- Remove item.
- Apply or remove coupon.
- Select address.
- Save address.
- Select delivery method.
- Continue.
- Go back.
- Select payment method.
- Confirm order.
- Retry payment.
- View order details.
- Return to shopping.

Verify that each control performs its advertised action, updates the appropriate state, invokes the correct service when necessary, and produces the correct resulting UI.

Remove decorative click handlers that do nothing.

If an action is unsupported by the application's actual capabilities, do not falsely present it as a working feature. Either implement its intended behavior or represent it honestly as unavailable, following the existing product requirements.

### C. Broken integrations

Investigate:

- API requests that are never called.
- UI state that does not reflect API responses.
- Data that is fetched but never used.
- Data that is modified locally but never persisted.
- Incorrect repository or service connections.
- Navigation destinations that cannot be reached.
- Callback or event handlers that are missing.
- Incorrect parameter passing.
- Inconsistent model mappings.
- Errors that are swallowed without user feedback.
- Outdated state or cached values.
- Incomplete create, read, update, and delete operations.
- Failed operations incorrectly represented as successful.

Trace each feature from the UI to the appropriate business logic and data source.

### D. Incomplete states

Every relevant feature must handle:

- Initial state.
- Loading state.
- Successful state.
- Empty state.
- Invalid input.
- Network failure.
- Backend rejection.
- Authentication expiration, where applicable.
- Retry behavior, where appropriate.
- Unexpected response or data.
- Duplicate requests.
- Cancellation or interruption.
- Relevant permission or configuration failures.

Do not allow failed operations to leave the interface in an ambiguous or permanently loading state.

## 6. ESTABLISH A SINGLE, CONSISTENT CHECKOUT STATE

Inspect and improve the application's existing state management so that all checkout phases share the same logical checkout context.

Avoid independently maintained copies of the cart, shipping selection, price breakdown, and payment status that can become inconsistent.

The shared checkout context should contain or reference the necessary information for the current session, such as:

- Current cart or cart identifier.
- Customer contact details.
- Selected delivery address.
- Selected fulfillment method.
- Eligible delivery options.
- Applied discounts or vouchers.
- Current pricing breakdown.
- Available payment methods.
- Checkout progress.
- Validation results.
- Submission and payment status.
- Relevant order identifiers after submission.

Derive values whenever possible instead of maintaining redundant copies.

Use the application's existing state management approach and architecture.

For example, adapt to the existing ViewModel and StateFlow pattern, repository-based architecture, reactive state management, or whatever mechanism the project already uses.

Do not introduce another state management system just for the checkout unless there is a compelling architectural reason.

### State consistency requirements

- UI components must render from the appropriate state source.
- User actions must trigger explicit state changes or business operations.
- API results must update the correct state.
- Stale asynchronous responses must not overwrite newer valid choices.
- Loading indicators must reflect actual operations.
- Failed actions must not accidentally commit invalid state.
- Changing an earlier phase must invalidate dependent values when necessary.
- Totals must be recalculated when their underlying inputs change.
- Navigating between phases must not silently discard valid information.
- The screen must recover correctly after common Android lifecycle events.
- Sensitive payment information must not be stored in ordinary application state or logs when inappropriate.

Implement clear ownership of checkout data and avoid unnecessary duplication between screens, repositories, and view models.

## 7. PRICING, DISCOUNTS, AND TOTAL CALCULATION

Ensure that checkout pricing is internally consistent and derived from valid data.

Determine how the existing application calculates:

- Item subtotals.
- Quantity-based totals.
- Discounts.
- Coupons and vouchers.
- Delivery charges.
- Taxes.
- Service fees.
- Other applicable charges.
- Final payable amount.

Reuse the existing pricing rules whenever they are correct.

Do not create conflicting pricing calculations in different checkout screens.

Where the client needs to display an estimated total, use a consistent pricing model. Before the order is accepted, ensure the authoritative backend or trusted transaction-processing layer validates the final amount.

Define and maintain a clear monetary calculation strategy, including currency handling and rounding behavior.

Use suitable numeric representations for money; avoid floating-point calculations that can introduce financial inaccuracies.

If a price changes between cart creation and order submission, apply the existing pricing policy and communicate relevant changes to the customer before final confirmation when required.

Do not silently charge a different amount from the amount confirmed by the customer.

## 8. PAYMENT, ORDER, AND TRANSACTION RELIABILITY

Treat financial operations as transaction-sensitive functionality.

Inspect the existing payment and order architecture and introduce safeguards appropriate to its capabilities.

### Requirements

- Prevent duplicate order submissions.
- Prevent duplicate payment initiation caused by repeated clicks.
- Use idempotency mechanisms where supported.
- Do not trust client-side payment success flags.
- Verify payment results using the appropriate trusted source.
- Handle delayed or asynchronous provider callbacks.
- Account for pending payments and uncertain network outcomes.
- Distinguish payment cancellation, failure, pending status, and success.
- Keep order and payment statuses consistent with the actual transaction outcome.
- Handle inventory reservations or stock updates according to existing business rules.
- Recover safely when an operation succeeds remotely but the client does not receive the response.
- Avoid clearing the customer's cart prematurely.
- Avoid exposing secret keys, tokens, credentials, or sensitive payment information.

Where the system supports multiple vendors or multiple fulfillment groups, ensure that order submission and payment handling conform to the existing business model.

Do not claim that order submission and payment are atomic unless the backend actually guarantees that behavior.

If a required transactional safeguard cannot be implemented entirely within the Android application, identify the backend change needed and implement the client-side integration accordingly.

Create a polished, production-quality checkout experience inspired by Shopify's usability principles without copying Shopify's exact branding.
